19Skills(可重用指令包 + 技能范围工具)

SKILL.md + 资源 + 工具模式 + Shell 模式(实验性)+ Agent Skills 规范对齐

一句话定性:Skill = name + description + content(指令主体)+ 可选资源,符合 Agent Skills 规范,从文件系统/类路径/编程方式加载,通过 activate_skill 工具按需加载到上下文。2 种模式:工具模式(安全,推荐)+ Shell 模式(实验性,不安全)。⚠️ 实验性 API。

核心思想:LLM 初始上下文保持简洁,只有技能名 + 描述的目录;需要执行时 LLM 调 activate_skill("name") 才把详细指令注入上下文 —— 类似"按需加载的 skill library",不是一次性塞满。

1. 业务场景

老板:"我们的 AI 客服现在 system prompt 已经塞了 8000 字(订单处理/退换货/物流查询/发票申请/投诉升级 5 大场景)。每加一个新场景就要重训,Token 费蹭蹭涨。怎么办?"

解法:用 Skill 把每个场景的指令(SKILL.md)+ 资源(模板/规则)拆成独立文件。系统 prompt 只放技能目录(5 个名字 + 一句话描述),LLM 看到用户问题匹配某技能时,才调 activate_skill("order-process") 加载那一个的详细指令 —— 上下文减半,Token 费 -40%,加新场景零改动。

6 个 Skills 能解决的事

  • 📚 Prompt 工程瘦身 — System prompt 8000 → 500(只剩技能目录),LLM 按需加载,Token 费砍 40%
  • 🧩 场景模块化 — 订单/退换货/物流/发票/投诉各一个 SKILL.md,加新场景零侵入
  • 🔒 工具按需暴露 — "订单处理"技能激活时,才把 validateOrder/chargePayment 等订单工具塞给 LLM(避免工具爆炸)
  • 📁 资源懒加载 — 技能指令里引用 references/tone-guide.md,LLM 用 read_skill_resource 按需读
  • 🔌 第三方技能复用 — Agent Skills 规范(agentskills.io 生态)发布的技能直接用,不用移植 Java
  • 📦 版本管理 — SKILL.md 是文件,进 Git,跟代码一起 review,改一次看得见

💡 什么时候不需要:单一场景 / 1-2 个工具 / system prompt 短 / LLM 一直用同一套指令 —— 直接写 system prompt 就行。Skill 是"场景多 + 工具多 + 指令长"的优化方案。

口诀:Skill = 技能目录(轻量 system prompt)+ 详细指令(按需 activate_skill)+ 资源(按需 read_skill_resource)。工具模式 = 安全(只调你注册的 Java 工具),Shell 模式 = 危险(LLM 可执行任意 shell 命令,慎用!)。99% 场景用工具模式,Shell 模式只用于本地原型。

2. 核心机制:Skill 是什么?

一个 Skill = name(机器读)+ description(LLM 读)+ content(指令主体,激活时注入)+ 可选 resources(按需读)。

2.1 SKILL.md 文件结构

skills/
├── docx/                          ← 技能 1:Word 文档编辑
│   ├── SKILL.md                   ← 必需:YAML 前置 + 指令主体
│   └── references/                ← 可选:资源子目录
│       └── tracked-changes.md
├── data-analysis/                 ← 技能 2:数据分析
│   └── SKILL.md
└── process-order/                 ← 技能 3:订单处理
    ├── SKILL.md
    └── references/
        └── refund-policy.md

SKILL.md 模板(YAML 前置 + Markdown 主体):

---
name: docx
description: Edit and review Word documents using tracked changes
---

When the user asks you to edit a Word document:
1. Always use tracked changes so edits can be reviewed.
2. ...

规则:

  • SKILL.md 必需,文件名固定
  • YAML 前置 必须有 name 和 description 两个字段
  • YAML 之后的 Markdown 是指令主体(LLM 激活技能时收到)
  • references/ 子目录下所有文件自动加载为 SkillResource
  • scripts/ 子目录不自动加载(给 Shell 模式用,工具模式跳过)

3. 加载方式(3 种)

3.1 从文件系统

<!-- pom.xml -->
<dependency>
    <groupId>dev.langchain4j</groupId>
    <artifactId>langchain4j-skills</artifactId>
    <version>1.11.8-beta19</version>
</dependency>
// 加载 skills/ 下所有一级子目录的技能
List<FileSystemSkill> skills = FileSystemSkillLoader.loadSkills(Path.of("skills/"));

// 加载单个技能
FileSystemSkill skill = FileSystemSkillLoader.loadSkill(Path.of("skills/docx"));

3.2 从类路径

适合技能打包在 JAR 或 src/main/resources:

src/main/resources/
└── skills/
    ├── docx/
    │   ├── SKILL.md
    │   └── references/tracked-changes.md
    └── data-analysis/
        └── SKILL.md
// 加载类路径下所有技能
List<FileSystemSkill> skills = ClassPathSkillLoader.loadSkills("skills");

// 加载单个
FileSystemSkill skill = ClassPathSkillLoader.loadSkill("skills/docx");

// 自定义 ClassLoader(可选)
FileSystemSkill skill = ClassPathSkillLoader.loadSkill("skills/docx", myClassLoader);

默认用线程上下文 ClassLoader。Spring Boot 场景下,放在 src/main/resources/skills/ 一打包,运行时 ClassPathSkillLoader.loadSkills("skills") 自动加载。

3.3 编程方式(从任意源)

技能不必基于文件,数据库/远程 API/运行时生成都行:

// 1. 纯编程构建
Skill skill = Skill.builder()
    .name("incident-response")
    .description("Step-by-step runbook for diagnosing and resolving production incidents")
    .content("""
        When a production alert fires:
        1. Call `fetchRecentLogs(serviceName)` to retrieve the last 5 minutes of logs.
        2. Call `checkServiceHealth(serviceName)` to get current health metrics.
        3. Based on the findings, call `createIncidentTicket(summary, severity)`.
        4. If severity is CRITICAL, also call `pageOnCall(incidentId)`.
        """)
    .build();

// 2. 附加资源
SkillResource reference = SkillResource.builder()
    .relativePath("references/tone-guide.md")
    .content("Use warm, concise language. Avoid jargon.")
    .build();

Skill skill2 = Skill.builder()
    .name("customer-support")
    .description("Handles customer support inquiries")
    .content("Follow the tone guide in references/tone-guide.md ...")
    .resources(List.of(reference))
    .build();

3 种方式可以混用 —— 先用 FileSystemSkillLoader 加载本地技能,再 toBuilder().resources(...).build() 加运行时资源。

4. 模式 1:工具模式(推荐,安全)

对应 Agent Skills 规范 中"基于工具的代理集成方法"。LLM 看不到文件系统 —— 所有技能内容和资源预加载到内存,通过 2 个工具返回:

工具何时注册作用
activate_skill总是注册LLM 调 activate_skill("name") → 把技能完整指令加载到上下文
read_skill_resource当至少一个技能有资源时LLM 调 read_skill_resource("name", "references/foo.md") → 按需读资源

核心安全保证:LLM 只能调你预定义的工具,不存在任意代码执行的风险。所有技能内容在 Java 侧预加载,LLM 调 activate_skill 返回的是内存中的字符串,不是从磁盘读。

4.1 接线 5 步

import dev.langchain4j.skills.Skills;
import dev.langchain4j.skills.FileSystemSkillLoader;
import java.nio.file.Path;

// 1. 加载技能
List<FileSystemSkill> loadedSkills = FileSystemSkillLoader.loadSkills(Path.of("skills/"));

// 2. 包成 Skills(可附加定制)
Skills skills = Skills.from(loadedSkills);

// 3. 构建 AI Service
MyAiService service = AiServices.builder(MyAiService.class)
    .chatModel(chatModel)
    .tools(new OrderTools())                       // ← 你的常规工具
    .toolProvider(skills.toolProvider())           // ← 技能 + 技能范围工具
    // 或: .toolProviders(myToolProvider, skills.toolProvider())
    .systemMessage("You have access to the following skills:\n"
        + skills.formatAvailableSkills()           // ← XML 格式技能目录
        + "\nWhen the user's request relates to one of these skills, "
        + "activate it first using the `activate_skill` tool before proceeding.")
    .build();

5 行(不算 import),完整接入 Skills。

4.2 formatAvailableSkills() 返回什么

XML 格式的技能目录(LangChain4j 自动注入到 system message):

<available_skills>
  <skill>
    <name>process-order</name>
    <description>Processes a customer order end-to-end</description>
  </skill>
  <skill>
    <name>data-analysis</name>
    <description>Analyse tabular data and produce charts</description>
  </skill>
</available_skills>

LLM 看到这段,就能根据 description 判断"用户问题匹配哪个技能",调 activate_skill("process-order") 加载那一个的详细指令。

4.3 实战:订单处理技能

skills/process-order/SKILL.md:

---
name: process-order
description: Processes a customer order end-to-end
---

To process an order:
1. Call `validateOrder(orderId)` to check the order is valid.
2. Call `reserveInventory(orderId)` to reserve the required stock.
3. Only if reservation succeeds, call `chargePayment(orderId)`.
4. Finally, call `sendConfirmationEmail(orderId)`.
If any step fails, call `rollbackOrder(orderId)` before reporting the error.

OrderTools.java(你的 Java 业务代码):

class OrderTools {
    @Tool("Validates a customer order by ID")
    String validateOrder(String orderId) {
        // 业务校验
        return "valid";
    }

    @Tool("Reserves inventory for an order")
    String reserveInventory(String orderId) {
        // 锁库存
        return "reserved";
    }

    @Tool("Charges payment for a customer order")
    String chargePayment(String orderId) {
        // 扣款
        return "charged";
    }
}

特点:

  • SKILL.md 描述"策略"(调用顺序、参数、错误处理)
  • OrderTools 是"执行"(类型安全的 Java 代码,单测可覆盖)
  • 策略和执行分离 —— 改流程只动 SKILL.md,改实现只动 Java

5. 模式 2:技能范围工具(Skill-Scoped)

常规 .tools(...) 一次全塞给 LLM,技能范围工具只在技能激活后才暴露 —— 保持 LLM 工具列表精简。

5.1 3 种挂载方式

方式 1:@Tool 注解方法(最简单)

Skill skill = Skill.builder()
    .name("process-order")
    .description("Processes a customer order end-to-end")
    .content("To process an order:\n  1. Call `validateOrder(orderId)`\n  2. Call `chargePayment(orderId)`")
    .tools(new OrderTools())   // ← @Tool 方法自动注册
    .build();

已加载的技能也能加工具(toBuilder()):

FileSystemSkill skill = FileSystemSkillLoader.loadSkill(Path.of("skills/process-order"));
Skill skillWithTools = skill.toBuilder()
    .tools(new OrderTools())
    .build();

方式 2:ToolProvider(动态工具,适合 MCP)

ToolProvider mcpToolProvider = McpToolProvider.builder()
    .mcpClients(mcpClient)
    .toolFilter((tool, mcpClient) -> tool.name().startsWith("inventory_"))
    .build();

Skill skill = Skill.builder()
    .name("inventory-management")
    .description("Manages warehouse inventory")
    .content("Use inventory tools to check stock levels and update quantities.")
    .toolProviders(mcpToolProvider)   // ← MCP 工具按需暴露
    .build();

方式 3:Map<ToolSpecification, ToolExecutor>(完全控制)

ToolSpecification validateOrder = ToolSpecification.builder()
    .name("validateOrder")
    .description("Validates a customer order by ID")
    .addParameter("orderId", JsonSchemaProperty.STRING,
        JsonSchemaProperty.description("The order ID"))
    .build();

ToolExecutor validateOrderExecutor = (request, memoryId) -> {
    String orderId = parseOrderId(request.arguments());
    return validate(orderId);
};

Skill skill = Skill.builder()
    .name("process-order")
    .description("Processes a customer order end-to-end")
    .content("1. Call `validateOrder(orderId)`")
    .tools(Map.of(validateOrder, validateOrderExecutor))
    .build();

3 种可以组合(@Tool 方法 + ToolProvider + Map 合并):

Skill skill = Skill.builder()
    .name("process-order")
    .description("Processes a customer order end-to-end")
    .content("...")
    .tools(new OrderTools())                            // ① @Tool 方法
    .tools(Map.of(validateOrder, validateOrderExecutor)) // ② Map
    .toolProviders(mcpToolProvider)                      // ③ ToolProvider
    .build();

5.2 技能范围工具工作原理

  1. 激活前:LLM 只看到 activate_skill(和 read_skill_resource),技能范围工具不出现在工具列表
  2. LLM 调 activate_skill("process-order") → 激活信息记入 ToolExecutionResultMessage
  3. 下一次 LLM 调用前(同一 AI Service 调用内),AI Service 重新评估动态工具提供者,技能范围工具(validateOrder)变可见
  4. LLM 同一 Service 调用内立即可调技能范围工具
  5. 技能范围工具在后续 AI Service 调用中保持可见,直到技能被停用

关键:激活是 sticky 的(一次激活,后续 AI Service 调用都能用),直到显式停用。

5.3 工具搜索协作(进阶)

技能可以跟 工具搜索(SimpleToolSearchStrategy)协同:

  • 技能范围工具不参与搜索(tool_search_tool 找不到它们)
  • 常规工具(.tools(...))可搜索
  • activate_skill 标 ALWAYS_VISIBLE,始终可调
MyAiService service = AiServices.builder(MyAiService.class)
    .chatModel(chatModel)
    .tools(new MySearchableTools())          // 常规工具,可搜索
    .toolProvider(skills.toolProvider())     // 技能范围工具,不参与搜索
    .toolSearchStrategy(new SimpleToolSearchStrategy())
    .systemMessage("...")
    .build();

6. 定制(覆盖默认工具名/描述/参数)

默认 activate_skill 工具名 / read_skill_resource 工具名 / 参数名都可以改:

Skills skills = Skills.builder()
    .skills(mySkills)
    .activateSkillToolConfig(ActivateSkillToolConfig.builder()
        .name("load_skill")                          // 工具名(默认 activate_skill)
        .description("Load a skill's full instructions")
        .parameterName("skill")                      // 参数名(默认 skill_name)
        .parameterDescription("The skill to load")
        .throwToolArgumentsExceptions(true)          // 抛 ToolArgumentsException
        .build())
    .readResourceToolConfig(ReadResourceToolConfig.builder()
        .name("read_resource")
        .description("Read a skill's resource file")
        .skillNameParameterName("skill")
        .skillNameParameterDescription("The skill name")
        .relativePathParameterName("path")
        .relativePathParameterDescription("Resource path")
        // .relativePathParameterDescriptionProvider(...) // 动态描述
        .throwToolArgumentsExceptions(true)
        .build())
    .build();

何时改:模型训练数据里 "activate_skill" 这个词出现得少 / 你的 system prompt 已经用了同名工具 / 想给 LLM 更明确的语义提示。

7. 模式 2:Shell 模式(实验性,慎用)

对应 Agent Skills 规范中"基于文件系统的代理集成方法"。LLM 自己跑 shell 命令读 SKILL.md,类似人类开发者浏览技能文件。

⚠️ 警告:Shell 执行本质上不安全。命令直接在宿主进程环境中运行,没有沙箱、没有容器化、没有权限限制。恶意/被 prompt 注入的 LLM 可以在跑应用的机器上执行任意命令。仅在完全信任输入并接受相关风险的受控环境中使用(如本地原型)。

7.1 工作原理

  1. System message 列出可用技能 + 绝对文件系统路径(<location> 字段)
  2. 用户问匹配某技能 → LLM 跑 cat /path/to/skills/docx/SKILL.md 读指令
  3. LLM 按指令跑进一步的 shell 命令(读资源 / 跑脚本)
  4. 只有 1 个工具:run_shell_command(替代 activate_skill + read_skill_resource)

7.2 依赖 + 接线

<!-- pom.xml -->
<dependency>
    <groupId>dev.langchain4j</groupId>
    <artifactId>langchain4j-experimental-skills-shell</artifactId>
    <version>1.11.8-beta19</version>
</dependency>
// 注意:用 ShellSkills 而不是 Skills
ShellSkills skills = ShellSkills.from(
    FileSystemSkillLoader.loadSkills(Path.of("skills/"))
);

MyAiService service = AiServices.builder(MyAiService.class)
    .chatModel(chatModel)
    .toolProvider(skills.toolProvider())
    .systemMessage("You have access to the following skills:\n"
        + skills.formatAvailableSkills()
        + "\nWhen the user's request relates to one of these skills, "
        + "read its SKILL.md before proceeding.")
    .build();

formatAvailableSkills() 输出多了 <location> 字段:

<available_skills>
  <skill>
    <name>docx</name>
    <description>Edit and review Word documents using tracked changes</description>
    <location>/path/to/skills/docx/SKILL.md</location>
  </skill>
</available_skills>

7.3 定制 Shell 工具

ShellSkills skills = ShellSkills.builder()
    .skills(mySkills)
    .runShellCommandToolConfig(RunShellCommandToolConfig.builder()
        .name("run_shell_command")
        .description("Execute a shell command")   // 默认含 OS 名
        .commandParameterName("cmd")              // 默认 command
        .commandParameterDescription("Shell command to run")
        .timeoutSecondsParameterName("timeout")   // 默认 timeout_seconds
        .workingDirectory(Path.of("/tmp/work"))   // 默认 user.dir
        .maxStdOutChars(20_000)                   // 默认 10_000
        .maxStdErrChars(20_000)
        .executorService(myExec)                  // 自定义执行器
        .throwToolArgumentsExceptions(true)
        .build())
    .build();

7.4 何时用 Shell 模式

  • ✅ 本地原型 / 实验(快速搭可用的工作流)
  • ✅ 用社区发布的第三方技能(agentskills.io 生态)而不移植 Java
  • ✅ 完全控制的环境(本地机器 / 受控 dev 环境)
  • ❌ 生产环境(任意命令执行风险)
  • ❌ 多用户 SaaS(一个用户 prompt 注入能影响整个服务器)

推荐路径:用 Shell 模式快速验证流程 → 方案成熟后,把"操作"逐步迁移到 Java 工具(类型安全 + 可测试),切到工具模式。

8. 工具模式 vs Shell 模式 决策

维度工具模式(推荐)Shell 模式(实验性)
模块langchain4j-skillslangchain4j-experimental-skills-shell

9. 决策树(怎么搭?)

10. 5 个避坑

⚠️ 坑 1:Shell 模式上生产
症状:本地原型调通了,直接发到生产,被 prompt 注入的 LLM 跑了 rm -rf /。
根因:Shell 模式没有沙箱,命令直接在宿主进程跑,权限跟启动 Java 进程的用户一样。
修法:生产 100% 用工具模式;Shell 模式只用于本地原型 / 调第三方社区技能。方案成熟后,把 shell 命令逐步迁移到 Java 工具(类型安全 + 可测试)。
⚠️ 坑 2:技能 description 写得太短 / 太长
症状:description 只有 "Processes orders"(太短,LLM 不知道何时调);description 写了 200 字调用步骤(太长,挤占目录,LLM 不读)。
根因:description 是"LLM 选技能的依据",应该简短 + 说明何时调。
修法:
  • ✅ "Processes a customer order end-to-end (validate → reserve → charge → confirm)"(10-30 字,带场景)
  • ❌ "Processes"(太短,场景不清)
  • ❌ "1. validate order... 2. reserve... 3. charge..."(太详细,挤)
详细步骤放 content(激活后才注入),不放 description(目录里一直显示)。
⚠️ 坑 3:忘记调 formatAvailableSkills()
症状:加载了技能,LLM 不知道有这些技能,从不调 activate_skill。
根因:技能是按需加载,LLM 初始上下文里只有目录。目录不注入 → LLM 瞎。
修法:systemMessage("..." + skills.formatAvailableSkills() + "..."),把 XML 目录拼到 system prompt。LangChain4j 不会自动帮你做。
⚠️ 坑 4:技能范围工具 + 工具搜索 配合错
症状:配置了工具搜索,技能激活了但 LLM 找不到 validateOrder(技能范围工具)。
根因:技能范围工具不参与工具搜索(tool_search_tool 找不到它们),只能通过 activate_skill 显式激活。
修法:
  • 技能范围工具:先 activate_skill,再用技能范围工具
  • 常规工具(.tools(...)):可搜索
  • 混合场景:技能范围工具 + 常规工具各管一段,LLM 自己协调
⚠️ 坑 5:实验性 API 当稳定 API 用 + Agent Skills 规范漂移
症状:升级 LangChain4j 1.x → 2.x,Skill.builder() 改名 / formatAvailableSkills() 输出格式变了;agentskills.io 规范新版本要求 SKILL.md 加 version 字段。
根因:Skills 明确"实验性 API";Agent Skills 规范也还在演进(类似 MCP 早期)。
修法:
  • 技能代码独立 skills/ 包,升级只改这个包
  • 大版本升级前看 release notes 的 Skills 章节
  • SKILL.md 写法留 兼容余地(description 不要依赖特定词,LLM 才能鲁棒匹配)
  • 关键流程在 content 里写容错(如 "If X fails, do Y")
