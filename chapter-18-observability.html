18Observability(看得见 LLM 在做什么)

8 AI Service 事件 · 5 Listener 体系 · OpenTelemetry · Micrometer · Langfuse · 6 业务场景

一句话定性:AI Service Observability(实验性)+ ChatModel/ModerationModel/Embedding/Store/Retriever Listener 5 套 + OpenTelemetry GenAI 语义约定(标准 span/属性) + Micrometer 指标(Token/延迟/错误率) + Langfuse/Phoenix 等三方 = LLM 应用"可观测、可回放、可统计、可告警"。⚠️ 实验性 API,Semantic Conventions 还在演进。

⚠️ 限定:AI Service 可观测性仅 AI Services 适用(跟 ch17 Guardrails 一样);ChatModel Listener 适用于所有实现该接口的模型。

1. 业务场景

老板:"咱们的 AI 客服上线 2 周,用户反馈'回答质量变差',但 LLM 厂商说他们的 API 没问题。Token 费也涨了 5 倍。怎么定位?"

解法:把每次 LLM 调用的 prompt / response / 耗时 / Token / 工具调用 / 错误 全部采集,接到监控平台。LangChain4j 提供 5 套 Listener 体系(AI Service / ChatModel / Moderation / Embedding / Store / Retriever),配合 OpenTelemetry(链路) + Micrometer(指标) + Langfuse(LLM 专用) 三件套。

6 个 Observability 能解决的事

  • 💰 Token 成本失控 — 某用户发了 1 万字 prompt,一晚上烧掉 $200,Langfuse 一查定位到,加 maxInputTokens 限制
  • 🐌 慢请求定位 — 用户报"我的请求超时",OTel 链路图显示是 Embedding 检索慢(数据库索引没建)而非 LLM
  • 🎯 幻觉排查 — 客服 Bot 答错,Langfuse 选中那条 trace,看到完整 prompt + 检索到的文档,5 秒复现
  • 📉 质量趋势 — 用户 thumbs down 标记到 Langfuse,运营每周拉 bad case 改 prompt
  • 🚨 错误告警 — Prometheus 配告警规则,LLM 错误率 > 5% 立刻发飞书/Slack
  • 📊 容量规划 — Micrometer 看 QPS + P99 延迟,提前 1 个月扩容,不会上线当天被打爆

💡 什么时候不需要:本地 demo、一次性脚本、个人玩具 —— 不需要。但凡上线给 ≥ 2 个用户用,至少加 ChatModelListener 记录 prompt/response(5 分钟搞定,出问题救你一命)。

口诀:观测三件套 = Logs(查一次)+ Metrics(看趋势)+ Traces(定位慢在哪)。Listener 是入口,OTel 是骨架,Micrometer 是肌肉,Langfuse 是大脑(LLM 专用语义)。早期 ChatModelListener + 日志就够,中型加 Langfuse,企业级上 OTel + Prometheus + Grafana 全套。

2. 三大支柱(Logs / Metrics / Traces)

支柱内容工具链解决什么问题
Logs 日志每次调用的 prompt、response、tool calls(可重放)SLF4J + logback + Langfuse"刚才那次回答是什么?"
Metrics 指标Token 用量、延迟、错误率、QPS(P50/P95/P99)Micrometer + Prometheus + Grafana"这一周延迟涨了吗?"
Traces 链路跨服务调用链,定位慢在哪一段OpenTelemetry + Jaeger / Tempo / Datadog / 阿里云 ARMS"这个请求哪一段慢?"

三者关系:1 次 LLM 调用会同时产生 1 条 trace(链路)+ 若干 metric(Token/延迟/错误)+ N 行 log(prompt/response/工具)。三者用同一 invocationId 关联(LangChain4j 在 InvocationContext.invocationId() 暴露)。

LangChain4j 监听器分 5 大类,各管一段:

4. AI Service 8 事件(实验性)

AI Service 调一次可能涉及多次 LLM 调用(有 Tools / Guardrails / RAG 时),8 个事件覆盖完整生命周期:

事件触发时机包含
AiServiceStartedEventLLM 调用开始时—
AiServiceRequestIssuedEvent每次向 LLM 发请求前(单次 Service 调用可能多次)system message / user message / tools / RAG 结果
AiServiceResponseReceivedEvent每次收到 LLM 响应后LLM 响应 + 对应请求
AiServiceErrorEventLLM 调用失败时(替代 Response)错误信息
AiServiceCompletedEventLLM 调用成功完成时调用结果
ToolExecutedEvent每次工具调用完成后工具请求 + 工具结果
InputGuardrailExecutedEvent每次输入护栏执行完输入 / 输出(成功/失败)/ 耗时
OutputGuardrailExecutedEvent每次输出护栏执行完输入 / 输出(success/failure/retry/reprompt)/ 耗时

注意:

  • 单次 Service 调用可能多次触发 Request/Response/Guardrail/Tool —— 因为有工具循环 + 重试
  • 不保证一一对应:成功路径有 Request + Response + Completed;失败路径有 Request + Error(没有 Response,也没有 Completed)
  • 实验性 API —— 大版本可能改(尤其事件名)

4.1 监听器实现示例

import java.time.Instant;
import java.util.Optional;
import java.util.UUID;
import dev.langchain4j.observability.api.event.AiServiceCompletedEvent;
import dev.langchain4j.observability.api.listener.AiServiceCompletedListener;
import dev.langchain4j.invocation.InvocationContext;

public class MyAiServiceCompletedListener
        implements AiServiceCompletedListener {

    @Override
    public void onEvent(AiServiceCompletedEvent event) {
        InvocationContext ctx = event.invocationContext();

        // 同一 invocation 的所有事件共享一个 invocationId
        UUID invocationId = ctx.invocationId();
        String interfaceName = ctx.interfaceName();
        String methodName = ctx.methodName();
        Object chatMemoryId = ctx.chatMemoryId();
        Instant timestamp = ctx.timestamp();
        Optional<Object> result = event.result();

        // 这里做日志 / 发送到 Langfuse / 上报指标
        log.info("AI Service completed: {}#{} inv={} mem={} result={}",
            interfaceName, methodName, invocationId, chatMemoryId, result);
    }
}

4.2 注册监听器

// 1. 准备监听器
MyAiServiceCompletedListener completedListener = new MyAiServiceCompletedListener();
MyAiServiceErrorListener errorListener = new MyAiServiceErrorListener();

// 2. AiServices builder 上注册
var assistant = AiServices.builder(MyAssistant.class)
    .chatModel(chatModel)
    .registerListener(completedListener)   // ← 一次性注册单个
    // 或:
    .registerListeners(List.of(completedListener, errorListener))  // 批量
    .build();

怎么关联一次调用的所有事件:用 InvocationContext.invocationId() —— 它是 UUID,同一 Service 调用产生的所有事件(Request / Response / Tool / Guardrail / Completed / Error)共享同一个 ID。

4.3 自定义事件 + 自定义监听器

AI Service 观测能力设计为可扩展:

  1. 实现 AiServiceEvent 接口 → 定义自己的事件
  2. 实现 AiServiceListener 接口 → 定义自己的监听器

5. ChatModelListener(最常用)

直接调 ChatModel 时也能挂监听器,3 个钩子:

import dev.langchain4j.model.chat.listener.ChatModelListener;
import dev.langchain4j.model.chat.listener.ChatModelRequestContext;
import dev.langchain4j.model.chat.listener.ChatModelResponseContext;
import dev.langchain4j.model.chat.listener.ChatModelErrorContext;

public class MyChatListener implements ChatModelListener {

    @Override
    public void onRequest(ChatModelRequestContext ctx) {
        // 1. 请求阶段:打印 prompt / 模型 / 参数
        var req = ctx.chatRequest();
        log.info("→ LLM 调用 model={} temp={} topP={} msgs={}",
            req.parameters().modelName(),
            req.parameters().temperature(),
            req.parameters().topP(),
            req.messages().size());
    }

    @Override
    public void onResponse(ChatModelResponseContext ctx) {
        // 2. 响应阶段:关键指标
        var resp = ctx.chatResponse();
        var usage = resp.metadata().tokenUsage();
        log.info("""
            ← LLM 响应:
              model:    {}
              finish:   {}
              耗时:     {}ms
              input:    {} tokens
              output:   {} tokens
              total:    {} tokens
            """,
            resp.metadata().modelName(),
            resp.metadata().finishReason(),
            ctx.requestTimeElapsed().toMillis(),
            usage.inputTokenCount(),
            usage.outputTokenCount(),
            usage.totalTokenCount()
        );
    }

    @Override
    public void onError(ChatModelErrorContext ctx) {
        // 3. 错误阶段:告警 + 重试策略
        log.error("LLM 调用失败,provider={} err={}",
            ctx.modelProvider(), ctx.error().getMessage());
        alertService.send("LLM 调用异常:" + ctx.error().getMessage());
    }
}

5.1 挂载方式

ChatModel model = OpenAiChatModel.builder()
    .apiKey(System.getenv("OPENAI_API_KEY"))
    .modelName("gpt-4o-mini")
    .listeners(List.of(

5.2 ChatModelListener 核心机制

行为说明
调用顺序按 List 迭代顺序,同步在同一线程
onRequest 触发每次 LLM 调用前调 1 次;若 LLM 内部 retry,不重复触发
onResponse 触发成功后调 1 次(LLM 内部 retry 不重复)
onError 触发失败时调 1 次(同上,不重复)
异常处理listener 抛异常只记 WARN,不影响后续 listener 执行,不影响主流程
attributes map跨钩子(onRequest → onResponse / onError)传数据;跨 listener 传数据

5.3 流式场景特殊行为

StreamingChatModel 上挂 listener 时:

  • onRequest 在调用线程触发
  • onResponse / onError 在不同线程触发(流式响应线程),线程上下文不自动传递
  • 用 attributes map 传上下文(比如 tenantId、correlationId)
  • onResponse 在 onCompleteResponse 之前触发;
  • onError 在 handler.onError 之前触发

5.4 attributes map + ChatRequestOptions

// 1. listener 跨钩子传数据(测耗时)
public class DurationListener implements ChatModelListener {
    @Override
    public void onRequest(ChatModelRequestContext ctx) {
        ctx.attributes().put("startNanos", System.nanoTime());
    }
    @Override
    public void onResponse(ChatModelResponseContext ctx) {
        long start = (long) ctx.attributes().get("startNanos");
        long duration = (System.nanoTime() - start) / 1_000_000;
        log.info("LLM 调用耗时: {}ms", duration);
    }
}

// 2. 跨调用传元数据(per-invocation)
ChatRequestOptions options = ChatRequestOptions.builder()
    .addListenerAttribute("tenantId", "tenant-123")     // 租户 ID
    .addListenerAttribute("correlationId", "corr-456")  // 链路追踪 ID
    .build();
model.chat(chatRequest, options);

关键:ChatRequestOptions.listenerAttributes 只在 LangChain4j 链路用,不发给 LLM 厂商(避免敏感字段泄露到 OpenAI / Anthropic)。

6. ModerationModelListener

3 个钩子(同 ChatModel),适用于 OpenAiModerationModel / MistralAiModerationModel / WatsonxModerationModel:

ModerationModelListener listener = new ModerationModelListener() {
    @Override
    public void onRequest(ModerationModelRequestContext ctx) {
        log.info("审查: {}", ctx.moderationRequest().texts());
        ctx.attributes().put("startTime", System.currentTimeMillis());
    }

    @Override
    public void onResponse(ModerationModelResponseContext ctx) {
        boolean flagged = ctx.moderationResponse().moderation().flagged();
        if (flagged) {
            String text = ctx.moderationResponse().moderation().flaggedText();
            alertService.send("Moderation 触发:" + text);
        }
        Long start = (Long) ctx.attributes().get("startTime");
        log.info("审查耗时: {}ms", System.currentTimeMillis() - start);
    }

    @Override
    public void onError(ModerationModelErrorContext ctx) {
        log.error("Moderation 调用失败", ctx.error());
    }
};

ModerationModel model = OpenAiModerationModel.builder()
    .apiKey(System.getenv("OPENAI_API_KEY"))
    .listeners(List.of(listener))
    .build();

public class MyRetrieverListener implements ContentRetrieverListener {

    @Override

9.4 实战 Micrometer 监听器(完全自定义)

不依赖官方 listener,自己写一个:

public class MetricsChatListener implements ChatModelListener {

    private final MeterRegistry registry;

    public MetricsChatListener(MeterRegistry registry) {
        this.registry = registry;
        // 预注册指标
        registry.counter("llm.requests.total", "model", "gpt-4o-mini");
        registry.counter("llm.tokens.input.total");
        registry.counter("llm.tokens.output.total");
        registry.counter("llm.errors.total");
        registry.timer("llm.call.duration");
    }

    @Override
    public void onResponse(ChatModelResponseContext ctx) {
        var usage = ctx.chatResponse().metadata().tokenUsage();
        registry.counter("llm.tokens.input.total")
            .increment(usage.inputTokenCount());
        registry.counter("llm.tokens.output.total")
            .increment(usage.outputTokenCount());
        registry.timer("llm.call.duration")
            .record(ctx.requestTimeElapsed());
    }

    @Override
    public void onError(ChatModelErrorContext ctx) {
        registry.counter("llm.errors.total").increment();
    }
}

挂到 Spring Boot:

@Configuration
public class ObservabilityConfig {

    @Bean
    public ChatModel chatModel(@Value("${openai.key}") String key,
                               MeterRegistry registry) {
        return OpenAiChatModel.builder()
            .apiKey(key)
            .modelName("gpt-4o-mini")
            .listeners(List.of(
                new MetricsChatListener(registry),                  // ① Prometheus
                new OpenTelemetryChatModelListener(otel),           // ② OTel 链路
                new LangfuseListener(langfuseConfig),               // ③ Langfuse
                new BusinessChatLogger()                            // ④ 业务日志
            ))
            .build();
    }
}

12. 5 个避坑

⚠️ 坑 1:把 listener 抛的异常当成主流程失败
症状:自定义 MyChatListener.onResponse() 调外部告警 API 抛了 NPE,整个 LLM 调用失败,用户看到 500。
根因:误以为 listener 抛异常会"冒泡"。
修法:官方明确 —— listener 抛异常只记 WARN,不影响后续 listener,不影响主流程。但你的业务逻辑该 try-catch 的还是要 try-catch,不要裸抛。
⚠️ 坑 2:流式场景下 listener 线程上下文丢失
症状:StreamingChatModel 上挂 listener,onResponse 里想拿 MDC.get("traceId") 关联日志,结果是 null。
根因:onResponse 在不同线程触发,MDC 没自动传。
修法:在 onRequest 里 ctx.attributes().put("traceId", MDC.get("traceId")),在 onResponse 里取出来。
⚠️ 坑 3:把敏感字段通过 listenerAttributes 发给 LLM 厂商
症状:用 addListenerAttribute("userId", realUserId) 传用户标识,LangChain4j 把它发到 OpenAI / Anthropic,触发隐私合规问题。
根因:误以为 listenerAttributes 会发给 LLM。
修法:官方明确 —— ChatRequestOptions.listenerAttributes 只在 LangChain4j 内部用,不发给 LLM 厂商。但其他 ChatRequest 字段(messages / metadata)会发。敏感字段别往 message 里塞。
⚠️ 坑 4:Langfuse / OTel 性能开销被低估
症状:每个请求都同步等 Langfuse 上报完成,LLM 调用 + 100ms 延迟,日均 100 万请求就是 100000 秒(27 小时!)CPU 时间浪费。
根因:Langfuse / OTel 默认是异步批上报,但你可能在测试环境用同步 SDK,生产没切。
修法:
  • OTel 用 BatchSpanProcessor(默认就是异步批)
  • Langfuse 用 LangfuseClient 异步 flush,别每次 flushSync()
  • 指标(Micrometer)也是异步采集,只暴露端点,不阻塞
⚠️ 坑 5:实验性 API 当稳定 API 用 + Semantic Conventions 漂移
症状:升级 LangChain4j 1.x → 2.x,AI Service 事件类改名 / 字段改了;升级 OTel SDK,GenAI Semantic Conventions 改了,Prometheus 指标名变了,Grafana 仪表盘全废。
根因:AI Service Observability 明确"实验性";OTel GenAI Conventions 也明确"实验性,可能改"。
修法:
  • 监听器代码独立 observability/ 包,升级只改这个包
  • 大版本升级前先看 release notes 的 observability 章节
  • OTel Semantic Conventions 用 官方版本(v1.39 起),别自己造
  • 关键仪表盘加 changelog,Conventions 变了能定位

14. 本章小结

  • 5 套 Listener 体系:AI Service(8 事件)/ ChatModel / Moderation / Embedding / Store / Retriever,统一 3 钩子
  • 观测三件套:Logs(查一次)+ Metrics(看趋势)+ Traces(定位慢在哪)
  • Listener 是入口,OTel 是骨架,Micrometer 是肌肉,Langfuse 是大脑(LLM 专用语义)
  • attributes map 跨钩子传(startNanos 测耗时);listenerAttributes 跨调用传(tenantId),不发 LLM
  • 早期:ChatModelListener + 日志;中型:+ Langfuse;企业:+ OTel + Micrometer + Prometheus + Grafana
  • 实验性 API:AI Service Observability + OTel GenAI Semantic Conventions 都标"实验性",大版本可能改
一句话总结:Observability 不是"上线出问题再补",而是"上线前 1 天挂 listener,出问题 5 分钟定位"。L1 必备:ChatModelListener + 业务日志;L2 进阶:Langfuse(prompt 反馈循环);L3 企业:OTel + Micrometer + Prometheus + Grafana(全栈三件套)。
