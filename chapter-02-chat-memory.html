多轮对话 · ChatMemory 抽象

02Chat Memory(聊天记忆)

LLM 本身无状态。多轮对话靠 ChatMemory 维护 ChatMessage 链表 + 驱逐策略 + 持久化。本章讲官方 2 种开箱即用实现 + 自定义 Store 接口。

一句话定性:ChatMemory = 一个 List<ChatMessage> 容器,带"按规则裁剪长度"和"按 ID 存外部数据库"两种能力。理解这个抽象,后面 AI Services 的 @MemoryId 就秒懂。

1. 业务场景

用户问:"我的订单到哪了?" → 客服查 + 回答。下一句:"那物流单号呢?"。

问题:第二次问的时候,模型并不知道你刚问了"我的订单到哪了"。因为每次 chat() 调用都是无状态的。

解法:把第一次的 UserMessage + AiMessage 塞到 ChatMemory,第二次 chat() 之前先把整段历史读出来,一起发给 LLM,模型就"记起来了"。

3 个真实使用场景

  • 多轮 AI 客服 — 上下文连贯,用户不用每句重说背景
  • AI 教学助手 — 记住学生之前问过的薄弱知识点,针对性讲解
  • 角色扮演 / 陪伴机器人 — 角色设定 + 长期记忆,聊 100 轮不"失忆"

2. 核心概念

ChatMemory 充当 ChatMessage 列表的容器,提供 3 件事:

  • 存储 — 内部就是个 List<ChatMessage>
  • 驱逐(eviction) — 消息太多时按规则裁剪,控制 token 上限
  • 持久化(store) — 把消息存到外部 DB / Redis

⚠️ 重要区分:LangChain4j 只提供记忆(memory)管理,提供历史(history)管理。如果你需要完整保留所有对话(不裁剪),ChatMemory 做不到,得自己用 ChatMemoryStore 实现。

3. 极简调用

创建一个"按消息条数裁剪"的 memory,10 轮内自动保留:

ChatMemory memory = MessageWindowChatMemory.withMaxMessages(10);

// 第一轮
memory.add(UserMessage.from("你好,我的名字叫张三"));
AiMessage ai1 = model.chat(memory.messages()).aiMessage();
memory.add(ai1);

// 第二轮:memory 里自动带上一轮的"我叫张三"
memory.add(UserMessage.from("我叫什么?"));
AiMessage ai2 = model.chat(memory.messages()).aiMessage();  // → "你叫张三"

4. 2 种开箱即用实现

① MessageWindowChatMemory(按条数裁剪)

ChatMemory memory = MessageWindowChatMemory.withMaxMessages(20);

保留最近 N 条消息,超出自动丢最老的。简单,适合 demo。

② TokenWindowChatMemory(按 token 数裁剪)

ChatMemory memory = TokenWindowChatMemory.withMaxTokens(2000, new OpenAiTokenizer());

保留最近 N 个 token 的消息,需要 tokenizer。生产推荐,严格控制费用。

5. 持久化:ChatMemoryStore 接口

默认 memory 存在内存,服务重启就丢。要持久化,实现 ChatMemoryStore 接口:

class PersistentChatMemoryStore implements ChatMemoryStore {
    @Override
    public List<ChatMessage> getMessages(Object memoryId) {
        // TODO: 从 MySQL / Redis 读这个 memoryId 的所有消息
    }

    @Override
    public void updateMessages(Object memoryId, List<ChatMessage> messages) {
        // TODO: 把消息写到 MySQL / Redis
    }

    @Override
    public void deleteMessages(Object memoryId) {
        // TODO: 删除该 memoryId 的所有消息
    }
}

用法:把 store 注入 memory

ChatMemory memory = MessageWindowChatMemory.builder()
        .maxMessages(10)
        .chatMemoryStore(new PersistentChatMemoryStore())
        .build();

6. 4 个特殊处理

① SystemMessage 特殊待遇

SystemMessage(你是一个 XX 助手)永远保留,不会被驱逐。其它消息被裁掉时它还在最前面。

② 工具消息防孤立

如果 AiMessage 里的 ToolExecutionRequest 被驱逐,对应的 ToolExecutionResultMessage 也会被自动驱逐。避免 OpenAI 等厂商报"孤立工具消息"错误。

7. memoryId 多用户隔离

Object memoryId 是关键 —— 它对应"哪个用户/哪个对话窗口"。同一进程内可以开 N 个 memory 实例,每个用户一个:

Map<String, ChatMemory> userMemories = new ConcurrentHashMap<>();

ChatMemory getMemory(String userId) {
    return userMemories.computeIfAbsent(userId, k ->
        MessageWindowChatMemory.withMaxMessages(10));
}

8. 避坑指南

坑 1 · 内存 memory 进程重启 = 全部失忆

MessageWindowChatMemory.withMaxMessages(N) 默认存堆内存。生产环境一定要接 ChatMemoryStore(Redis/MySQL),否则用户每次重启都"第一次见面"。

坑 2 · SystemMessage 不能用 chat() 字符串重载塞

想要"我的人设"提示词,必须 memory.add(SystemMessage.from(...))。用 chat("你叫小爱") 没用,只是普通 UserMessage。

坑 3 · 按条数裁剪不控制 token 费用

withMaxMessages(20) 看起来 20 条不多,但如果每条都很长(几 KB),总 token 可能超 8000。生产优先 TokenWindowChatMemory。

坑 4 · memoryId 一定要稳定,别每次新建

用 UUID.randomUUID() 当 memoryId = 每次创建新 memory = 用户"每次都失忆"。必须是用户 ID / 会话 ID这种稳定 key。

坑 5 · getMessages() 是热路径,别查慢库

每次 LLM 调用都会触发 store.getMessages(memoryId)。如果背后是 MySQL 全表扫描,直接拖垮接口。必须走主键查询 + 缓存。

9. 记忆口诀

🎓 4 行口诀

ChatMemory 是个 Message 容器, 三件事 存 裁 持久化
MessageWindow 按条裁, TokenWindow 按 token 卡
SystemMessage 永不被裁, 工具消息防孤立
memoryId 走用户 ID 稳定值, 重启靠 Store 不失忆
