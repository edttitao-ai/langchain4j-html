16MCP 模型上下文协议(Agent 接外部工具的 USB-C)

5 种 Transport · Client · Provider · Resources · Registry · 跨语言工具标准化

一句话定性:McpTransport(5 种连接方式)+ DefaultMcpClient(客户端)+ McpToolProvider(工具聚合)+ McpRegistryClient(服务器发现) = Agent 接外部工具的标准化协议(类似 USB-C)。MCP 是 Anthropic 2024 年发布的开放协议,让 LLM Agent 不用写 @Tool 适配就能调 GitHub / Slack / PostgreSQL / Google Maps 等任何暴露 MCP 的服务。做企业 Agent 集成外部系统(订单库 / 客服通知 / 代码审查),MCP 是 99% 的正解。

1. 业务场景

老板:"我们客服 AI 想直接查订单数据库、查物流系统、发 Slack 通知、调 GitHub 提交 bug,集成这些系统要多久?"
架构师:"传统方式:每个外部系统写一个 @Tool 适配器(GitHub API / Slack SDK / JDBC / Google Maps SDK),共 4 套集成 + 4 套鉴权 + 4 套维护,3 个月。"
老板:"MCP 呢?"
架构师:"2 周。每个外部系统装一个 MCP 服务器(NPM/Docker/官方提供),Java 侧只配 Transport,工具列表自动拉取。"

❌ 传统 @Tool 适配地狱(每个外部系统都要写一遍):

// 1. 写 GitHub @Tool 适配(自己封装 SDK)
@Tool("查询 GitHub Issue")
public String getIssue(@P("repo") String repo, @P("number") int number) {
    String token = System.getenv("GITHUB_TOKEN");
    return HttpClient.newHttpClient().send(
        HttpRequest.newBuilder()
            .uri(URI.create("https://api.github.com/repos/" + repo + "/issues/" + number))
            .header("Authorization", "Bearer " + token)
            .build(), BodyHandlers.ofString()
    ).body();
}

// 2. 写 Slack @Tool 适配(又一遍 SDK + auth)
@Tool("发 Slack 消息")
public String sendSlack(@P("channel") String channel, @P("msg") String msg) {
    String token = System.getenv("SLACK_TOKEN");
    return HttpClient.newHttpClient().send(...);
}

// 3. 写 PostgreSQL @Tool 适配(JDBC + SQL 注入防御 + 重试)
@Tool("查订单")
public String queryOrder(@P("sql") String sql) { ... }

// 问题:
// - 每个外部系统写一遍 @Tool(4 套代码 + 4 套 auth)
// - 外部 API 升级,要改所有 @Tool(GitHub v3 → v4)
// - 多个 AI Service 重复 @Tool 代码(订单查询 / 客服 AI / 数据分析)
// - 工具元数据不标准化(LLM 看到的是 @Tool 注释拼凑的 JSON Schema)

✅ MCP 标准化接入(一行配置接外部):

// 1. 装 GitHub MCP 服务器(NPM 一行)
McpTransport githubTransport = StdioMcpTransport.builder()
    .command(List.of("/usr/bin/npm", "exec", "@modelcontextprotocol/server-github"))
    .logEvents(true)
    .build();

// 2. 装 Slack MCP 服务器(Docker 一行)
McpTransport slackTransport = StreamableHttpMcpTransport.builder()
    .url("https://mcp.slack.com/mcp")  // 官方托管
    .logRequests(true)
    .build();

// 3. 装 PostgreSQL MCP 服务器(stdio Docker)
McpTransport pgTransport = DockerMcpTransport.builder()
    .image("mcp/postgres")
    .dockerHost("unix:///var/run/docker.sock")
    .build();

// 4. 多客户端聚合(1 个 Provider 聚合 3 个 MCP 客户端)
McpToolProvider toolProvider = McpToolProvider.builder()
    .mcpClients(
        DefaultMcpClient.builder().key("github").transport(githubTransport).build(),
        DefaultMcpClient.builder().key("slack").transport(slackTransport).build(),
        DefaultMcpClient.builder().key("postgres").transport(pgTransport).build()
    )
    .failIfOneServerFails(false)  // 单个挂了不影响其他
    .filterToolNames(
        "get_issue", "create_issue", "list_issues",   // GitHub
        "send_message", "list_channels",               // Slack
        "query_orders", "get_product"                  // Postgres
    )
    .build();

// 5. 注入 AI Service
Assistant assistant = AiServices.builder(Assistant.class)
    .chatModel(chatModel)
    .toolProvider(toolProvider)
    .build();

String response = assistant.chat("查订单 #20260615-A,如果有质量问题,在 #ops 频道发 Slack");
// → Agent 自动调用 postgres.query_orders + slack.send_message
//   不用写任何 @Tool 代码!

// 优势:
// - MCP 服务器由官方维护,API 升级服务端解决(零客户端修改)
// - 工具元数据 JSON Schema 标准,LLM 看到规范的 tool description
// - 多 AI Service 共享同一个 MCP 客户端池
// - 任何语言都能用(Python / Go / Node 都能接)

🔥 真实成本案例:某跨境电商要接入 10 个外部系统(订单库 / 物流 / 支付 / Slack / GitHub / Jira / Salesforce / Google Maps / AWS S3 / Slack)。传统 @Tool 适配:10 套集成 + 3 个 Java 工程师 × 3 个月 = ¥45 万(人力)。MCP 接入:10 个 MCP 服务器部署(多数官方提供)+ 1 个 Java 工程师 × 2 周 = ¥5 万。省 ¥40 万,上线快 5 倍。

6 个 MCP 能解决的事

  • 📦 跨境订单直查 — PostgreSQL MCP 让 LLM 直接查订单库(SQL 自动转),不用写中间层 API
  • 📞 客服消息群发 — Slack/钉钉 MCP 让 Agent 自动发内部通知(售后 / 财务 / 仓储)
  • 🗺️ 物流地址验证 — Google Maps MCP 让 Agent 校验地址 / 计算运费 / 估算送达时间
  • 📋 代码仓库协同 — GitHub MCP 让 Agent 自动开 Issue / Review PR(代码审查自动化)
  • 📑 实时法规检索 — Brave Search / Google Search MCP 让 Agent 联网查最新跨境法规
  • 🔌 跨语言 AI 协同 — Python 写的 AI 助手 + Java 写的订单系统,通过 MCP 互调(协议中立)
口诀:MCP 就像USB-C(一个接口接所有外设)。传统 @Tool 适配像每个外设买一根专用的线(USB-A / Mini-USB / Lightning / DC 圆口...)。2024 年起所有 AI 工具都该走 MCP。

2. 核心架构

MCP 是客户端-服务器架构,基于 JSON-RPC 2.0 协议通信。

【MCP 4 层架构】

  ┌──────────────────────────────────────────────────┐
  │ AI Agent / AI Service(Java 侧 LangChain4j)        │
  │   Assistant assistant = AiServices.builder()...  │
  └─────────────────────┬────────────────────────────┘
                        │ 调用 tool(name, args)
                        ▼
  ┌──────────────────────────────────────────────────┐
  │ McpToolProvider(工具聚合器)                      │
  │   - 多客户端聚合(GitHub + Slack + Postgres)       │
  │   - 名称白名单 / BiPredicate 过滤                │
  │   - 工具重命名(toolNameMapper)                    │
  └─────────────────────┬────────────────────────────┘
                        │ 转发
                        ▼
  ┌──────────────────────────────────────────────────┐
  │ DefaultMcpClient(MCP 客户端)                     │
  │   - 工具缓存(cacheToolList)                       │
  │   - 工具列表 + Resources + Prompts               │
  └─────────────────────┬────────────────────────────┘
                        │ JSON-RPC 2.0
                        │ (5 种 Transport 之一)
                        ▼
  ┌──────────────────────────────────────────────────┐
  │ MCP 服务器(外部进程)                            │
  │   - NPM 子进程(stdio)                           │
  │   - Docker 容器(Docker stdio)                    │
  │   - HTTP 服务(Streamable HTTP)                   │
  │   - WebSocket 服务                               │
  │   - HTTP+SSE 服务(传统,弃用)                    │
  └──────────────────────────────────────────────────┘

2.1 三步上手

// 1. Transport(选择连接方式)
McpTransport transport = StdioMcpTransport.builder()
    .command(List.of("/usr/bin/npm", "exec", "@modelcontextprotocol/server-everything@0.6.2"))
    .logEvents(true)
    .build();

// 2. Client(从 Transport 创建客户端)
McpClient mcpClient = DefaultMcpClient.builder()
    .key("MyMCPClient")           // 可选,但多个客户端必填
    .transport(transport)
    .cacheToolList(true)          // 默认 true
    .build();

// 3. Provider(从 Client 创建工具聚合)
McpToolProvider toolProvider = McpToolProvider.builder()
    .mcpClients(mcpClient)
    .build();

3. 5 种 Transport(选连接方式)

3.1 stdio(本地子进程)

用途:MCP 服务器作为本地子进程,通过 stdin/stdout 通信。最常用。

// 启动 NPM 包形式的 MCP 服务器
McpTransport transport = StdioMcpTransport.builder()
    .command(List.of(
        "/usr/bin/npm", "exec",
        "@modelcontextprotocol/server-github@1.0.0"
    ))
    .logEvents(true)        // 打印 MCP 协议交互
    .logRequests(true)
    .logResponses(true)
    .build();

// 也可以直接执行本地二进制
.command(List.of(
    "/usr/local/bin/my-custom-mcp-server",
    "--config", "/etc/mcp/config.json"
))
💡 适用场景:开发环境 / 本地工具(NPM 包 / Python 脚本 / Go 二进制)。简单稳定,无需网络。

3.2 Streamable HTTP(SSE 流式,新一代标准)

用途:MCP 服务器作为HTTP 服务,客户端发 POST 请求,服务器可以一次性响应或开 SSE 流发多次。2024+ 新标准,推荐生产用。

// 远程 MCP 服务器
McpTransport transport = StreamableHttpMcpTransport.builder()
    .url("http://localhost:3001/mcp")     // 服务器 POST 端点
    .logRequests(true)
    .logResponses(true)
    .subsidiaryChannel(true)              // 启用 GET-based SSE(接收服务器主动通知)
    .build();

// 重要:可流式 HTTP 是 MCP 新标准(2024 年底发布)
// 老式 HTTP/SSE 已被弃用,见 3.4
⚠️ 自动重连:SSE 流断开后,传输会自动重连(默认 5 秒,遵循服务器 retry 设置)。

3.3 WebSocket(实验性)

用途:MCP 服务器作为 WebSocket 服务。实验性,目前只与 Quarkus MCP 服务器扩展兼容。

McpTransport transport = WebSocketMcpTransport.builder()
    .url("ws://localhost:3001/mcp/ws")
    .logResponses(true)
    .logRequests(true)
    .build();

3.4 HTTP/SSE(传统,已弃用 ⚠️)

用途:传统 MCP 协议传输。已被官方弃用,未来将移除。仅维护老项目兼容。

// 传统方式:两个 URL(sseUrl + POST 由服务器动态返回)
McpTransport transport = HttpMcpTransport.builder()
    .sseUrl("http://localhost:3001/sse")     // SSE 通道 URL
    .logRequests(true)
    .logResponses(true)
    .build();

// ⚠️ 已弃用,新项目请用 Streamable HTTP

3.5 Docker stdio(容器化)

用途:MCP 服务器以容器镜像分发,用 Docker stdio 跑。生产隔离首选。

// 1. 加依赖
<dependency>
    <groupId>dev.langchain4j</groupId>
    <artifactId>langchain4j-mcp-docker</artifactId>
    <version>1.11.8-beta19</version>
</dependency>

// 2. Docker Transport
McpTransport transport = DockerMcpTransport.builder()
    .image("mcp/time")                                  // 官方镜像
    .dockerHost("unix:///var/run/docker.sock")           // Docker daemon
    .logEvents(true)
    .build();

// 3. 或本地构建的镜像
.image("mycompany/mcp-internal-tools:1.2.0")
💡 优势:容器隔离 + 标准化分发 + 版本管理 + 多实例编排。生产推荐(特别是接入多个内部 MCP 服务时)。

4. McpClient 客户端

DefaultMcpClient 是 MCP 协议 Java 侧默认实现。它从 Transport 拉取工具列表,并维护内部缓存。

// 基础创建
McpClient mcpClient = DefaultMcpClient.builder()
    .key("github-mcp")         // 客户端唯一标识(多客户端必填)
    .transport(transport)      // 4 种 Transport 之一
    .cacheToolList(true)       // 默认 true,工具列表缓存
    .build();

// 工具缓存策略
// 默认 cacheToolList(true) → 拉一次,除非服务器通知"列表变了"否则不重拉
// cacheToolList(false)     → 每次 AI 调用都重拉(慢,慎用)

// 手动清缓存(服务器动态新增工具后)
mcpClient.evictToolListCache();

// 手动执行工具(在 AI Service 外)
ToolExecutionRequest request = ToolExecutionRequest.builder()
    .name("get_issue")
    .arguments("{\"repo\": \"langchain4j\", \"number\": 1234}")
    .build();
String result = mcpClient.executeTool(request);

// 列出所有可用工具
ListToolsResult tools = mcpClient.listTools();
💡 key 的作用:多 MCP 客户端时,key 用于区分(过滤 / 日志 / 路由)。多个 client 时必填(否则冲突)。

5. McpToolProvider 工具聚合

Provider 聚合多个 MCP 客户端的工具,统一暴露给 AI Service。可配置过滤 / 容错 / 重命名。

5.1 多客户端聚合

McpToolProvider toolProvider = McpToolProvider.builder()
    .mcpClients(githubClient, slackClient, postgresClient)  // 多个
    .failIfOneServerFails(false)  // 单个挂了不影响其他
    .build();

5.2 filterToolNames 名称白名单

// MCP 服务器可能暴露几十个工具,LLM 用不到全部
// 用 filterToolNames 只暴露必要的(降低 LLM 幻觉)
McpToolProvider toolProvider = McpToolProvider.builder()
    .mcpClients(githubClient)
    .filterToolNames(
        "get_issue", "get_issue_comments", "list_issues"  // 只读权限
        // 没有 create_issue / delete_issue / update_issue
    )
    .build();

5.3 filter BiPredicate 动态过滤

用途:多 MCP 客户端同名工具冲突时,按规则选哪个。

// 两个 MCP 客户端都有 echoInteger,只保留 numeric-mcp 的
McpToolProvider toolProvider = McpToolProvider.builder()
    .mcpClients(mcpClient1, mcpClient2)
    .filter((mcpClient, tool) ->
        !tool.name().startsWith("echoInteger")
        || mcpClient.key().equals("numeric-mcp")
    )
    .build();

// filter 多次调用是 AND 合取

5.4 toolNameMapper 重命名

// 工具名不直观 / 冲突时,可重命名
McpToolProvider toolProvider = McpToolProvider.builder()
    .mcpClients(githubClient, slackClient)
    .toolNameMapper((mcpClient, tool) ->
        mcpClient.key() + "__" + tool.name()
    )
    .build();
// GitHub 的 get_issue → github__get_issue(避免冲突,带命名空间)

5.5 动态添加 / 移除客户端

// 运行时动态管理(支持 hot reload)
toolProvider.addMcpClient(newMcpClient);    // 加
toolProvider.removeMcpClient("old-client"); // 删
toolProvider.clearMcpClients();             // 全清

6. 集成到 AI Service

6.1 方式一:toolProvider 注入(推荐)

Bot bot = AiServices.builder(Bot.class)
    .chatModel(chatModel)
    .toolProvider(toolProvider)   // ← 注入 MCP 工具聚合
    .build();

String response = bot.chat("查订单 #20260615-A 的状态");
// AI 自动决定调 postgres.query_orders("order_id=20260615-A")

6.2 方式二:tools Map 手动

// 更精细控制(每个工具自己写 ToolExecutor)
Map<ToolSpecification, ToolExecutor> tools = mcpClient.listTools().stream()
    .collect(Collectors.toMap(
        tool -> tool,
        tool -> new McpToolExecutor(mcpClient)
    ));

Bot bot = AiServices.builder(Bot.class)
    .chatModel(chatModel)
    .tools(tools)  // ← 手动 Map
    .build();
💡 选哪种:多数项目用方式一(toolProvider 简单)。需要自定义执行逻辑 / 加缓存 / 重试时用方式二。

7. MCP Resources(不只是 Tools)

MCP 服务器不只暴露 Tools,还暴露 Resources(文件 / 数据库 / API 数据)。Tools 是 LLM 主动调用,Resources 是 LLM 读取。

7.1 DefaultMcpResourcesAsToolsPresenter(自动暴露)

// MCP 服务器暴露的资源(类似 Web 文件系统)
ReadResourceResult result = mcpClient.readResource("file:///docs/catalog.json");
// 返回 McpTextResourceContents 或 McpBlobResourceContents

// 自动通过 Tools 暴露给 AI(LLM 不需要直接调 readResource)
// 设了 presenter 后,ToolProvider 自动加两个合成工具:
McpToolProvider toolProvider = McpToolProvider.builder()
    .mcpClients(mcpClient)
    .resourcesAsToolsPresenter(new DefaultMcpResourcesAsToolsPresenter())
    .build();

// 自动多了两个工具:
// 1. list_resources → 列出所有资源(JSON 数组)
// 2. get_resource(server_name, uri) → 读取指定资源

// LLM 自动决定:"先 list_resources 看有什么,再 get_resource 读详情"
💡 Tools vs Resources:Tools 是动作(改状态:发消息 / 创建订单);Resources 是数据(读状态:文件 / 配置)。MCP 用同一协议暴露两种,统一接口。

8. MCP Registry(服务器发现)

MCP Registry 是官方 MCP 服务器目录(https://registry.modelcontextprotocol.io),可搜索公开的 MCP 服务器。

// 1. 创建 Registry 客户端(默认指向官方 registry)
McpRegistryClient registry = DefaultMcpRegistryClient.builder()
    .baseUrl("https://registry.modelcontextprotocol.io")  // 默认就是这个
    .build();

// 2. 搜索 MCP 服务器
McpServerListRequest request = McpServerListRequest.builder()
    .search("github")   // 关键字搜索
    .limit(10)           // 最多 10 个结果
    .build();

List<McpServer> servers = registry.listServers(request);

// 3. 拿到服务器后,自动创建 MCP 客户端
for (McpServer server : servers) {
    System.out.println(server.name() + " - " + server.description());
    // 安装命令:npm install @modelcontextprotocol/server-XXX
}
⚠️ 安全警告:从 Registry 找到的 MCP 服务器可以执行任意代码(尤其 stdio / Docker 本地跑)。运行前务必验证可信度。LangChain4j 默认不自动执行,需手动确认。

9. 5 种 Transport 选型决策

Transport连接方式推荐场景
stdio本地子进程 stdin/stdout开发 / 本地工具 / NPM 包 / 简单稳定
Streamable HTTPHTTP POST + SSE 流生产首选/ 远程服务 / 跨网络 / 新标准
WebSocketWS 双工连接Quarkus MCP / 实验性 / 双工需求
HTTP/SSE(弃用)传统 SSE + POST仅老项目兼容/ 新项目不要用
Docker stdio容器内 stdio生产隔离 / 多 MCP 服务 / 版本管理

决策流程:

  • 开发 + 单一工具 → stdio(NPM 包)
  • 生产 + 远程服务 → Streamable HTTP(新标准)
  • 生产 + 多 MCP 服务 + 隔离 → Docker stdio
  • Quarkus 生态 → WebSocket
  • 老 MCP 1.0 服务器 → HTTP/SSE(短期兼容,长期升级)

10. 8 避坑

坑 1 ❌ 多客户端 key 不设导致冲突

症状:IllegalStateException: duplicate key
根因:多个 MCP 客户端时没设 key,默认冲突。
修法:每个客户端都设唯一 key(如 "github-mcp" / "slack-mcp")。

坑 2 ❌ 工具过多导致 LLM 幻觉

症状:LLM 调错工具,或干脆不调。
根因:MCP 服务器暴露几十个工具,LLM 选择困难,幻觉率高。
修法:严格 filterToolNames(只暴露 5-10 个相关工具),filter BiPredicate 二次过滤。

坑 3 ❌ 工具列表缓存过期

症状:MCP 服务器加了新工具,AI 还是看不到。
根因:cacheToolList=true(默认)缓存到进程生命周期,服务器端加工具不通知。
修法:服务器动态加工具后,调 mcpClient.evictToolListCache() 清缓存。

坑 4 ❌ Registry 服务器未验证就跑

症状:执行了恶意 MCP 服务器,被攻击(读文件 / 装后门)。
根因:MCP 服务器有任意代码执行权限(尤其 stdio / Docker)。
修法:只用官方 / 大厂 / 公司内部的 MCP 服务器;第三方服务器先读源码 + 沙箱跑。

坑 5 ❌ Docker Transport 缺 /var/run/docker.sock 权限

症状:Permission denied 连不上 Docker daemon。
根因:Java 进程用户(非 root)没 docker group 权限。
修法:1)把用户加 docker 组;2)用 rootless docker;3)改用远程 Docker host(TLS 认证)。

坑 6 ❌ HTTP/SSE 用了 Streamable HTTP 代码

症状:连不上服务器 / 数据乱码。
根因:MCP 1.0 用 HttpMcpTransport(sseUrl),新 MCP 用 StreamableHttpMcpTransport(url),混用失败。
修法:看服务器版本选 Transport;新项目只用 Streamable HTTP。

坑 7 ❌ toolExecutionRequest arguments 传 Map

症状:IllegalArgumentException: arguments must be JSON string
根因:arguments() 是 JSON 字符串,不是 Map。
修法:

// ❌ Map
.arguments(Map.of("a", "b"))

// ✅ JSON 字符串
.arguments("{\"a\": \"b\"}")

坑 8 ❌ 同步阻塞调用导致 MCP 雪崩

症状:多个 AI 调用并发,MCP 服务器被打爆。
根因:MCP Transport 默认同步阻塞,没有限流。
修法:1)MCP 服务器侧加限流;2)Provider 用线程池隔离;.executor(Executors.newFixedThreadPool(10));3)failIfOneServerFails(false) 避免一个挂全挂。
