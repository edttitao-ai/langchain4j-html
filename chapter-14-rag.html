14RAG 检索增强生成(给 LLM 接外挂大脑)

3 种 RAG 风格 · Embedding + 向量库 · 5 大 Advanced 组件 · 15+ 向量库选型

一句话定性:EmbeddingModel(文本→向量)+ EmbeddingStore(向量库) + ContentRetriever(相似度检索) = 给 LLM 接外挂大脑。Easy RAG 一行启动 / Naive RAG 5 件套手动拼 / Advanced RAG 5 大组件模块化。做企业知识库 / 跨境法规检索 / 客服 SOP 库,RAG 是 99% 的正解。

1. 业务场景

老板:"我们客服 AI 把 2023 年的冬季爆款推荐给客户,客户来骂说这些 SKU 早下架了。能不能让 AI 知道我们的实时商品库?"

❌ 闭卷模式的死循环(LLM 只靠训练数据):

用户:推荐 3 款冬季保暖手套
AI:  1. 北面防滑雪地手套(NF0A7RKA) - 经典款
    2. 哥伦比亚男士抓绒手套 - 性价比之选
    3. 巴塔哥尼亚 R1 户外手套 - 专业户外

    ↑ (LLM 装死,因为训练数据截止后它不知道)
用户:多少钱?
AI:  据我所知,北美官网通常售价 $49.99
    ↑ (幻觉!实际 $39.99 已是历史价格)
用户:跟第二款比呢?
AI:  抱歉,我不清楚您指哪款...
    ↑ (上下文丢光,典型闭卷)

    1. 北面防滑雪地手套 - $39.99 - 库存 230 件
    2. 优衣库 HEATTECH 触屏手套 - ¥99 - 库存 1200 件

    主要优点是触屏兼容和轻薄保暖。

    第 2 款更适合日常通勤和轻度户外。

🔥 真实成本案例:跨境电商客服 200 座席 × 8 小时 × 50 咨询/人/天 = 8 万次咨询/天。AI 答不上的 30% 转人工,人工成本 ¥15/通 × 2.4 万通 = ¥36 万/月。RAG 把 AI 命中率从 60% → 88%,转人工率 30% → 12%,月省 ¥26 万(人力 + 培训 + 流失)。

2. 核心架构

RAG 在 LangChain4j 里分两阶段:索引(离线)和检索(在线)。

【索引阶段 · 离线,可定时 cron 跑】
原始文档 ──→ DocumentLoader ──→ Document[] (带 metadata)
                                          │
                                          ▼
                            DocumentSplitter(切 chunk)
                                          │
                                          ▼
                              TextSegment[] (300 token/chunk)
                                          │
                                          ▼
                            EmbeddingModel(文本→向量)
                                          │
                                          ▼
                            EmbeddingStore. add(向量, segment)
                                          │
                                          ▼
                            ┌──────────────────────────┐
                            │ EmbeddingStore(向量数据库) │
                            │  InMemory / PGVector /   │
                            │  Qdrant / Pinecone / Milvus │
                            └──────────────────────────┘

【检索阶段 · 在线,每次用户问问题】
用户 Query ──→ EmbeddingModel(向量化)
                       │
                       ▼
              EmbeddingStore.search(相似度 top-K)
                       │
                       ▼
              Content[] top-3~5(最相关的片段)
                       │
                       ▼
              ContentInjector(注入到 UserMessage)
                       │
                       ▼
              LLM(带着 context 回答)
                       │
                       ▼
              返回给用户

2.1 三种 RAG 风格总览

风格上手难度代码量可定制性适用阶段
Easy RAG⭐ 一行启动5-10 行低(SPI 自动装载)POC / 原型验证
Naive RAG⭐⭐ 手动拼30-50 行中(每件可换)中小业务 / 单一知识库
Advanced RAG⭐⭐⭐ 模块化80-150 行高(5 大组件自由组合)企业级 / 多源 / 多语言

2.2 五个 Advanced RAG 核心组件

组件职责默认实现
QueryTransformer把 1 个 Query 改成 N 个(压缩 / 扩展 / 重写)DefaultQueryTransformer(透传)
QueryRouter决定 Query 走哪个 ContentRetrieverDefaultQueryRouter(单一路由)
ContentRetriever从某个数据源拉 Content(向量库 / Web / SQL)EmbeddingStoreContentRetriever
ContentAggregator合并多路召回的 Content,排序 / 去重DefaultContentAggregator(按分数)
ContentInjector把 Content 注入 UserMessage(默认拼到前面)DefaultContentInjector
💡 入口:所有 5 大组件通过 RetrievalAugmentor 统一调度。LangChain4j 默认实现 DefaultRetrievalAugmentor 把 5 大组件按顺序串起来,99% 场景够用。

3. Easy RAG(一键启动)

Easy RAG是 LangChain4j 给的"零配置"模式:加一个 langchain4j-easy-rag 依赖,它通过 SPI 自动装载 DocumentParser (Apache Tika) + DocumentSplitter + EmbeddingModel(bge-small-en-v1.5,ONNX 离线运行)+ InMemoryEmbeddingStore。5 行代码就有一个 RAG。

3.1 加依赖

<dependency>
    <groupId>dev.langchain4j</groupId>
    <artifactId>langchain4j-easy-rag</artifactId>
    <version>1.11.8-beta19</version>
</dependency>
<!-- 它会传递依赖:
     - langchain4j-core
     - Apache Tika(自动解析 PDF/DOCX/HTML...)
     - bge-small-en-v1.5 ONNX 模型(离线 embedding)
     - langchain4j-document-parser-apache-tika
     - InMemoryEmbeddingStore 默认实现 -->

3.2 5 行代码完整 RAG

// 1. 加载文档(默认从 /home/langchain4j/documentation 读所有文件)
List<Document> documents = FileSystemDocumentLoader
    .loadDocuments("/path/to/your/docs");

// 2. 创建内存向量库
InMemoryEmbeddingStore<TextSegment> embeddingStore = new InMemoryEmbeddingStore<>();

// 3. 一行 ingest(SPI 自动切分 + embed + 入库)
EmbeddingStoreIngestor.ingest(documents, embeddingStore);

// 4. 配 ChatModel
ChatModel chatModel = OpenAiChatModel.builder()
    .apiKey(System.getenv("OPENAI_API_KEY"))
    .build();

// 5. 创建带 RAG 的 AI Service
Assistant assistant = AiServices.builder(Assistant.class)
    .chatModel(chatModel)
    .contentRetriever(EmbeddingStoreContentRetriever.from(embeddingStore))
    .build();

String answer = assistant.chat("什么是 RAG?");
// → 自动从 docs 检索 + 拼到 prompt + 调 LLM

💡 底层 SPI 自动做了什么:

  • DocumentParser:ApacheTikaDocumentParser(PDF/DOCX/HTML/MD 全自动)
  • DocumentSplitter:DocumentByParagraphSplitter(每段 ≤ 300 token,30 token overlap)
  • EmbeddingModel:AllMiniLmL6V2QuantizedEmbeddingModel(ONNX,24MB,CPU 跑,MTEB 榜优秀)
  • EmbeddingStore:InMemoryEmbeddingStore(重启丢数据,只适合 POC)
⚠️ Easy RAG 的代价:默认配置适合英文(模型 bge-small-en)+ 内存存储(重启丢数据)+ 单一 chunking 策略(段落级)。生产环境要做企业级 RAG,必须升级到 Naive RAG 或 Advanced RAG。

3.3 文件加载方式

// 1. 普通加载(只读当前目录,不递归)
List<Document> docs = FileSystemDocumentLoader.loadDocuments("/docs");

// 2. 递归加载子目录
List<Document> docs = FileSystemDocumentLoader.loadDocumentsRecursively("/docs");

// 3. 通配符过滤(只读 PDF)
PathMatcher matcher = FileSystems.getDefault().getPathMatcher("glob:*.pdf");
List<Document> docs = FileSystemDocumentLoader.loadDocuments("/docs", matcher);

// 4. 递归 + 通配符(用 **)
PathMatcher matcher = FileSystems.getDefault().getPathMatcher("glob:**.pdf");
List<Document> docs = FileSystemDocumentLoader
    .loadDocumentsRecursively("/docs", matcher);

// 5. 从 URL 加载(网页文档)
Document doc = UrlDocumentLoader.load("https://example.com/article.html", new ApacheTikaDocumentParser());

// 6. 从 Classpath 加载(Spring Boot resources)
List<Document> docs = ClassPathDocumentLoader.loadDocuments("/knowledge", new ApacheTikaDocumentParser());

4. Naive RAG(5 件套手动拼)

Naive RAG就是不用 Easy RAG 的 SPI 自动装配,自己手动配 5 件套:DocumentLoader → DocumentSplitter → EmbeddingModel → EmbeddingStore → ContentRetriever。每个件可换,生产环境就靠这层。

4.1 完整代码:跨境电商 SKU 知识库

// 1. DocumentLoader —— 加载本地 SKU 文档(可能还有商品图说明)
List<Document> documents = FileSystemDocumentLoader
    .loadDocumentsRecursively("/data/products/2026");

// 2. DocumentSplitter —— 中文按段落切,500 token/chunk,100 token overlap
DocumentSplitter splitter = DocumentByParagraphSplitter.builder()
    .maxChunkSize(500)       // 中文 500 token ≈ 750 字
    .chunkOverlap(100)       // 重叠 100 token 避免边界语义丢
    .tokenizer(new HuggingFaceTokenizer("gpt2"))  // 用 GPT2 tokenizer 算 token
    .build();

// 3. EmbeddingModel —— 用 OpenAI text-embedding-3-small(中英都好,便宜)
EmbeddingModel embeddingModel = OpenAiEmbeddingModel.builder()
    .apiKey(System.getenv("OPENAI_API_KEY"))
    .modelName("text-embedding-3-small")  // 1536 维,$0.02/百万 token
    .build();

// 4. EmbeddingStore —— 用 PGVector(公司已有 PostgreSQL,无需额外组件)
EmbeddingStore<TextSegment> embeddingStore = PGVectorEmbeddingStore.builder()
    .host("localhost")
    .port(5432)
    .database("ecommerce")
    .user("postgres")
    .password("secret")
    .table("product_embeddings")
    .dimension(1536)  // 必须跟 embedding 模型维度匹配
    .build();

// 5. ContentRetriever —— 检索 top-5,最低相似度 0.7
ContentRetriever contentRetriever = EmbeddingStoreContentRetriever.builder()
    .embeddingStore(embeddingStore)
    .embeddingModel(embeddingModel)
    .maxResults(5)            // 取 top-5
    .minScore(0.7)            // 相似度 < 0.7 不要
    .filter(metadataKey("category").isEqualTo("electronics"))  // 元数据过滤
    .build();

// 6. AI Service 注入
ChatModel chatModel = OpenAiChatModel.builder()
    .apiKey(System.getenv("OPENAI_API_KEY"))
    .modelName("gpt-4o-mini")
    .build();

Assistant assistant = AiServices.builder(Assistant.class)
    .chatModel(chatModel)
    .contentRetriever(contentRetriever)
    .chatMemory(MessageWindowChatMemory.withMaxMessages(10))
    .build();

String answer = assistant.chat("推荐一款夏季蓝牙耳机,预算 200 以内");

4.2 自定义 Ingestor 流程

生产环境通常手动控制 ingest 流程(要加 metadata、要清洗、要 skip):

EmbeddingStoreIngestor ingestor = EmbeddingStoreIngestor.builder()
    .documentSplitter(splitter)
    .embeddingModel(embeddingModel)
    .embeddingStore(embeddingStore)
    .documentTransformer(new MetadataTransformer())  // 加元数据
    .build();

// 一次 ingest 全部
ingestor.ingest(documents);

// 手动逐个 ingest(适合大数据量,分批)
for (Document doc : documents) {
    Document enriched = doc.transform(document -> {
        document.metadata().put("source", "product_catalog");
        document.metadata().put("indexed_at", Instant.now().toString());
        return document;
    });
    ingestor.ingest(List.of(enriched));
}

4.3 检索参数调优

EmbeddingStoreContentRetriever.builder()
    .embeddingStore(embeddingStore)
    .embeddingModel(embeddingModel)
    // 召回数 vs 准确率权衡
    .maxResults(3)       // 默认 5,过多会稀释 LLM 注意力
    .minScore(0.7)       // 低于这个分数认为不相关,丢弃
    // 元数据过滤:分类、日期、来源
    .filter(metadataKey("category").isEqualTo("electronics"))
    .filter(metadataKey("indexed_at").isGreaterThan("2026-01-01"))
    // 动态 metadata 表达式(运行时从 user 查询拿)
    .dynamicFilter(query -> {
        String userRole = query.metadata().chatMemoryId().toString();
        return metadataKey("visibility").isEqualTo("public");
    })
    .build();

5. Advanced RAG(模块化 5 组件)

Advanced RAG 把 5 大组件独立出来,通过 RetrievalAugmentor 串成 pipeline。每个组件可替换、可组合、可扩展。

5.1 RetrievalAugmentor 入口

// 1. 创建 5 大组件
QueryTransformer queryTransformer = new CompressingQueryTransformer(chatModel);
ContentRetriever retriever1 = EmbeddingStoreContentRetriever.from(store1);  // 商品库
ContentRetriever retriever2 = EmbeddingStoreContentRetriever.from(store2);  // 评价库
QueryRouter queryRouter = new DefaultQueryRouter(retriever1, retriever2);  // 多路路由
ContentAggregator aggregator = new DefaultContentAggregator();
ContentInjector injector = new DefaultContentInjector();

// 2. 拼成 RetrievalAugmentor
RetrievalAugmentor augmentor = DefaultRetrievalAugmentor.builder()
    .queryTransformer(queryTransformer)
    .queryRouter(queryRouter)
    .contentAggregator(aggregator)
    .contentInjector(injector)
    .build();

// 3. 挂到 AI Service
Assistant assistant = AiServices.builder(Assistant.class)
    .chatModel(chatModel)
    .retrievalAugmentor(augmentor)  // ← 跟 .contentRetriever() 二选一
    .build();

5.2 QueryTransformer(查询变换)

把 1 个用户问题改写成更适合检索的 N 个问题。

// 1. CompressingQueryTransformer —— 把"他住在哪" + 历史 → "John Doe 住在哪"
QueryTransformer compressing = new CompressingQueryTransformer(chatModel);

// 场景:用户追问
// 用户: 介绍一下 John Doe
// AI:    John Doe 是我们的 CTO...
// 用户: 他住哪?     ← 本身检索不到"他"是谁
// ↓ CompressingQueryTransformer 改写为:
//      "John Doe 住在哪?"   ← 带历史合并,检索能命中

// 2. ExpandingQueryTransformer —— 把 1 个问题改成 N 个变体
QueryTransformer expanding = new ExpandingQueryTransformer(chatModel);
// 用户: 蓝牙耳机
// ↓ 改写为:
//   1. "无线蓝牙耳机"
//   2. "蓝牙 5.0 耳机"
//   3. "运动蓝牙耳机"
//   4. "降噪蓝牙耳机"
//   → 每个 query 都去检索,合并去重,提升召回率

// 3. Step-back prompting
QueryTransformer stepBack = new StepBackQueryTransformer(chatModel);
// 用户: gpt-4o-mini 价格?
// ↓ 改写为:
//   "OpenAI 各模型价格对比"   ← 先查通用,再聚焦

// 4. HyDE(Hypothetical Document Embeddings)
QueryTransformer hyde = new HyDEQueryTransformer(chatModel);
// 用户: 怎么优化 PG 性能?
// ↓ 让 LLM 生成"假想答案",用假想答案的向量去检索
//   (原理:假想答案的向量比问题更接近真实文档)

5.3 QueryRouter(多路路由)

把 1 个 Query 分发到不同数据源。

// 多路路由:商品库 + 评价库 + Web Search
ContentRetriever productRetriever = EmbeddingStoreContentRetriever.from(productStore);
ContentRetriever reviewRetriever = EmbeddingStoreContentRetriever.from(reviewStore);
ContentRetriever webRetriever = WebSearchContentRetriever.from(
    TavilyWebSearchEngine.builder()
        .apiKey(System.getenv("TAVILY_API_KEY"))
        .build()
);

// 默认路由:每个 retriever 都查一遍
QueryRouter router = new DefaultQueryRouter(productRetriever, reviewRetriever, webRetriever);

// LLM 路由:让 LLM 决定查哪个
QueryRouter llmRouter = new LanguageModelQueryRouter(chatModel, productRetriever, reviewRetriever, webRetriever);

// 自定义路由:按 metadata 路由
QueryRouter customRouter = query -> {
    String category = query.metadata().invocationParameters().get("category");
    if ("product".equals(category)) return List.of(productRetriever);
    if ("review".equals(category)) return List.of(reviewRetriever);
    return List.of(productRetriever, reviewRetriever);  // 默认全查
};

5.4 ContentAggregator(多路合并)

合并多路召回结果,排序、去重、过滤。

// 默认按相似度分数排序
ContentAggregator aggregator = new DefaultContentAggregator();

// 自定义:重排序(Re-rank)
ContentAggregator rerankAggregator = new ReRankingContentAggregator(
    new CohereReranker(System.getenv("COHERE_API_KEY")),  // 第三方重排序模型
    // 或者本地 ONNX:new BgeRerankerModel()
    3  // 保留 top-3
);

// 自定义:按 metadata 加权
ContentAggregator weightedAggregator = (query, contents) -> {
    return contents.stream()
        .sorted((a, b) -> {
            double scoreA = a.score() + scoreBoost(a.textSegment());
            double scoreB = b.score() + scoreBoost(b.textSegment());
            return Double.compare(scoreB, scoreA);
        })
        .limit(5)
        .collect(Collectors.toList());
};

选型决策:

  • 纯英文 + POC → bge-small-en-v1.5(ONNX,免费)
  • 纯中文 + POC → bge-small-zh-v1.5 或 DashScope
  • 生产英文 / 中英 → text-embedding-3-small(便宜 + 质量好)
  • 生产中文合规 → DashScope text-embedding-v3(国内)
  • 多语言(跨境) → Cohere embed-multilingual-v3 或 BgeM3
  • 高准确(法律 / 医疗) → text-embedding-3-large 或 bge-large-en-v1.5
💡 维度必须匹配:EmbeddingModel 的 dimension 必须跟 EmbeddingStore 的 dimension 一致(改模型要重建库)。生产切模型时记得 reindex()。

8. Document Splitter 速查

Splitter切分依据chunk 数适用
DocumentByParagraphSplitter段落边界少结构化文档(合同 / 报告)
DocumentBySentenceSplitter句子边界中叙述性文档(博客 / 文章)
DocumentByCharacterSplitter固定字符数多无明显结构(日志 / OCR)
DocumentByRegexSplitter正则表达式自定义Markdown / 代码块 / 自定义段落
DocumentByWordSplitter单词边界多英文 / 多语言混合

8.1 推荐 chunk 配置

// 中文场景(企业知识库 / 商品库)
DocumentByParagraphSplitter.builder()
    .maxChunkSize(500)       // 500 token ≈ 750 中文字
    .chunkOverlap(100)       // 100 token 重叠(20%),保语义连续
    .tokenizer(new HuggingFaceTokenizer("gpt2"))  // 通用 tokenizer
    .build();

// 英文场景(API 文档 / 论文)
DocumentByParagraphSplitter.builder()
    .maxChunkSize(300)       // 英文 300 token ≈ 200 词
    .chunkOverlap(30)        // 30 token ≈ 10%
    .build();

// 自定义:Markdown 按 ## 切分
DocumentByRegexSplitter.builder()
    .regex("(?m)^##\\s")      // 匹配 Markdown 二级标题
    .build();
💡 Chunk Size 经验值:太小 → 语义断裂、检索不到完整概念;太大 → 噪声多、稀释 LLM 注意力。中文 400-600 token,英文 200-400 token 是 sweet spot。必须有 overlap(10-20%),否则边界处语义会丢。

9. 10 避坑

坑 1 ❌ 用 InMemoryEmbeddingStore 做生产

症状:重启服务后所有 Embedding 丢失,AI 答不上任何问题。
根因:InMemoryEmbeddingStore 只存 JVM 堆,进程退出即丢。
修法:生产用 PGVector / Qdrant / Pinecone 等持久化向量库。

坑 2 ❌ Embedding Model 维度不匹配

症状:IllegalArgumentException: Dimension mismatch
根因:换 embedding 模型(如 bge-small 384 → text-embedding-3-small 1536)但向量库还是旧维度。
修法:换模型时先 drop 表重建,再 reindex。维度一旦确定,不要随便换。

坑 3 ❌ Easy RAG 默认是英文模型

症状:中文知识库检索效果差,语义匹配不上。
根因:Easy RAG SPI 默认装载 bge-small-en-v1.5,只懂英文。
修法:

// 显式注入中文模型
EmbeddingModel embeddingModel = new BgeSmallZhV15QuantizedEmbeddingModel();
EmbeddingStoreIngestor.builder()
    .embeddingModel(embeddingModel)
    .embeddingStore(embeddingStore)
    .build()
    .ingest(documents);

坑 4 ❌ 没有 overlap 导致边界语义丢

症状:检索"合同违约责任"时,关键段落正好在 chunk 边界被切断。
根因:chunkOverlap=0 导致两个相邻 chunk 完全不重叠。
修法:始终设 chunkOverlap = maxChunkSize * 10%~20%。

坑 5 ❌ 没设 minScore,垃圾结果污染 LLM

症状:LLM 答非所问,prompt 里被注入了 5 段不相关的文档。
根因:EmbeddingStoreContentRetriever 默认 maxResults=5, minScore=0,返回所有"勉强相关"的段。
修法:

EmbeddingStoreContentRetriever.builder()
    .embeddingStore(store)
    .embeddingModel(model)
    .maxResults(3)      // 少而精,3-5 个 sweet spot
    .minScore(0.7)      // 过滤低分(< 0.6 几乎不相关)
    .build();

坑 6 ❌ Chunk 太大,塞爆 LLM 上下文窗口

症状:长文档(5000 token)整段塞进 prompt,LLM 报错 "context length exceeded"。
根因:maxChunkSize=10000(> LLM 上下文窗口的 1/4)。
修法:单 chunk 不超过 LLM 上下文窗口的 10%(GPT-4 是 128K,所以单 chunk 不超过 12K token)。生产一般 300-800 token。

坑 7 ❌ Advanced RAG 里 QueryTransformer 顺序反了

症状:用 ExpandingQueryTransformer 生成 5 个变体,然后 CompressingQueryTransformer 压缩回 1 个,等于白干。
根因:Compressing 应该是 Expanding 之前的步骤(先精炼问题,再扩展变体),或者只用其中一个。
修法:

// 正确顺序:先 Compressing(去噪)→ 再 Expanding(扩召回)
DefaultRetrievalAugmentor.builder()
    .queryTransformers(
        new CompressingQueryTransformer(chatModel),  // 先
        new ExpandingQueryTransformer(chatModel)    // 后
    )

坑 8 ❌ CompressingQueryTransformer 让上下文爆炸

症状:多轮对话每轮都让 LLM 重新压缩整段历史,token 用量翻倍。
根因:CompressingQueryTransformer 默认读 query.metadata().chatMemory() 全量历史。
修法:对长对话(> 20 轮),只压缩最近 N 条:

CompressingQueryTransformer compressing = new CompressingQueryTransformer(chatModel, 5);  // 只压最近 5 条

坑 9 ❌ Reranker 没调,精度差

症状:召回 50 个候选段,top-3 注入 prompt,但实际上 top-3 不一定是最好的。
根因:向量相似度对长文档 / 复杂查询精度有限(只看语义不看相关性)。
修法:加 Re-ranking 步骤,把 50 候选用专门的重排序模型重排,取真正 top-3:

ContentAggregator aggregator = new ReRankingContentAggregator(
    new CohereReranker(System.getenv("COHERE_API_KEY")),
    3  // 最终注入 top-3
);

坑 10 ❌ Metadata 没设,检索过滤失效

症状:.filter(metadataKey("category").isEqualTo("electronics")) 不生效。
根因:ingest 时没给 document 加 category 这个 metadata,数据库里都是空。
修法:ingest 时显式注入 metadata:

ingestor.ingest(documents.stream()
    .map(doc -> doc.transform(d -> {
        d.metadata().put("category", "electronics");
        d.metadata().put("indexed_at", Instant.now().toString());
        return d;
    }))
    .collect(Collectors.toList()));

11. 本章小结 + 下一章

  • 3 种 RAG:Easy RAG 一行启动(POC) / Naive RAG 5 件套手动(中小)/ Advanced RAG 5 大组件(企业级)
  • 核心流程:索引(离线 DocumentLoader → Splitter → Embed → Store)+ 检索(在线 Query → Embed → Search → Inject)
  • 5 大组件:QueryTransformer(改写)→ QueryRouter(分发)→ ContentRetriever(拉数据)→ ContentAggregator(合并)→ ContentInjector(注入 prompt)
  • 向量库选型:POC InMemory / 中小 PGVector Redis / 中等 Qdrant / 大 Milvus Pinecone
  • 10 避坑:InMemory 不可生产 / 维度匹配 / Easy RAG 默认英文 / 必须 overlap / minScore 过滤 / chunk 大小 / Transformer 顺序 / Compressing 上下文爆炸 / Reranker 必要性 / Metadata 必填
