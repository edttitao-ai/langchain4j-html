12日志记录(LLM 行为的黑匣子)

SLF4J 门面 + 3 个开关 + 3 套集成 + 敏感信息脱敏 + MDC 链路追踪

一句话定性:SLF4J + .logRequests(true) / .logResponses(true) / .logRequestsAndResponses(true) 三个开关 + 任意日志后端(Logback / Log4j2 / JUL) = LangChain4j 全链路可观测。生产环境 必开,否则 LLM 调用像黑盒 —— prompt 发了什么、响应回了什么、token 用了多少全看不见。

1. 业务场景

老板:"上周客服 AI 投诉量突然涨了 30%,客服说 AI 答非所问。能不能把 AI 的对话记录拉出来看看它到底说了啥?"

解法:LangChain4j 用 SLF4J 作为日志门面,三个开关控制请求/响应的日志输出。配上 Logback 的 Console / File / JSON 输出,就能把 LLM 行为"刻进石板"。

5 个 Logging 能解决的事

  • 🪲 调试 AI 行为 — 用户反馈"AI 答非所问",拉日志看 prompt 实际发给 LLM 的内容,排查是 prompt 拼错了还是 LLM 偏题
  • 💰 算 LLM 成本 — 响应日志里带 token 用量(tokenUsage.inputTokenCount() / outputTokenCount()),按用户/会话聚合,算出谁在烧钱
  • 📜 合规审计 — 金融/医疗行业必须保留 AI 决策依据("为什么拒绝这笔贷款"),日志是审计证据
  • 📈 性能分析 — 响应日志带耗时,可以分析"哪些 prompt 慢、哪些模型快、什么时候超时"
  • 🛡️ 故障排查 — 线上 AI 突然 500,看错误日志知道是 prompt 超长截断、API key 过期、还是 rate limit

💡 没日志的代价:真实事故 —— 某跨境电商 AI 客服把内部折扣策略"无意"透露给客户,事后复盘才发现是 prompt 拼接时把 internalConfig 拼进去了。没有日志,事故永远查不清。

口诀:生产环境 logRequests=true + logResponses=true 必开,脱敏 必做,MDC 链路 必加。三必三不做,事故来了能甩锅。

2. 核心机制

LangChain4j 的日志体系是三层结构:

┌─────────────────────────────────────────────────────┐
│ 第 1 层:SLF4J 门面(你的代码只认这个,不耦合具体实现) │
│   LangChain4j 内部所有日志走 SLF4J                 │
├─────────────────────────────────────────────────────┤
│ 第 2 层:LangChain4j 的 3 个开关                      │
│   .logRequests(true)         — 打印发出去的请求      │
│   .logResponses(true)        — 打印收到的响应        │
│   .logRequestsAndResponses() — 一行打请求+响应      │
├─────────────────────────────────────────────────────┤
│ 第 3 层:日志后端(选一个或多个)                       │
│   Logback(推荐)/ Log4j2 / JUL / JCL                 │
│   输出到 Console / File / JSON / Syslog / Kafka      │
└─────────────────────────────────────────────────────┘

2.1 SLF4J 门面是什么

SLF4J(Simple Logging Facade for Java)是一个日志抽象层。LangChain4j 写日志只调 SLF4J API,你项目里接什么日志框架(Logback / Log4j2 / JUL)由你决定 —— 换日志框架不用改 LangChain4j 代码。

2.2 3 个开关的区别

开关输出内容日志量适用场景
.logRequests(true)只打印 请求(发给 LLM 的 prompt)每请求 1 行想知道 AI "问了什么"
.logResponses(true)只打印 响应(LLM 回复内容)每响应 1 行想知道 AI "答了什么"
logRequestsAndResponses(true)请求+响应同一行打每调用 1 行想快速看 prompt ↔ response 对应关系

⚠️ 默认行为:全部关闭(false)。生产环境不显式开启 = 看不到任何 LLM 调用日志。

2.3 日志级别对照

SLF4J LevelLangChain4j 用在哪建议
ERRORLLM 调用异常 / API key 失效 / 网络超时生产必保留
WARNprompt 被截断 / 重试 / 模型降级生产必保留
INFO请求/响应内容(开 logRequests 时)生产建议保留(INFO 级别)
DEBUG详细请求/响应 + token 数调试时开,生产关闭
TRACE完整 HTTP body + header深排查,性能损耗大

3.2 加 Logback 依赖

SLF4J 只是个接口,必须有实现。LangChain4j 不会自己带 Logback,你要在 pom.xml 加:

<!-- pom.xml -->
<dependency>
    <groupId>org.slf4j</groupId>
    <artifactId>slf4j-api</artifactId>
    <version>2.0.13</version>
</dependency>

<!-- Logback 是最常用的 SLF4J 实现 -->
<dependency>
    <groupId>ch.qos.logback</groupId>
    <artifactId>logback-classic</artifactId>
    <version>1.5.8</version>
</dependency>

💡 为什么选 Logback:Spring Boot 默认用它,性能好(异步日志器),配置灵活(logback.xml 强大)。不建议用 Log4j 1.x(已 EOL,2015 年停止维护)。

3.3 最小 Logback 配置

<!-- src/main/resources/logback.xml -->
<configuration>
    <!-- 输出到 Console -->
    <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
        <encoder>
            <pattern>%d{HH:mm:ss.SSS} [%thread] %-5level %logger{36} - %msg%n</pattern>
        </encoder>
    </appender>

    <!-- LangChain4j 包设 DEBUG(看到请求/响应细节) -->
    <logger name="dev.langchain4j" level="DEBUG"/>

    <!-- 其他包默认 INFO -->
    <root level="INFO">
        <appender-ref ref="CONSOLE"/>
    </root>
</configuration>

4. Spring Boot 集成

Spring Boot 默认带 Logback,所以 不用额外加依赖。只需要在 application.properties 配开关 + 在 logback-spring.xml 配格式。

4.1 application.properties

# application.properties
# LangChain4j 自己的日志开关(关键!没这俩就是黑盒)
langchain4j.open-ai.chat-model.log-requests=true
langchain4j.open-ai.chat-model.log-responses=true

# Spring Boot 自带的日志级别
logging.level.root=INFO
logging.level.com.yourcompany=DEBUG

4.2 logback-spring.xml(Spring 增强版)

logback-spring.xml 比 logback.xml 强 —— 支持 <springProfile> 标签,可以在不同环境用不同配置。

<!-- src/main/resources/logback-spring.xml -->
<?xml version="1.0" encoding="UTF-8"?>
<configuration>
    <!-- 控制台 appender -->
    <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
        <encoder>
            <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level %logger{36} [traceId=%X{traceId:-}] - %msg%n</pattern>
        </encoder>
    </appender>

    <!-- 文件 appender(每天切割) -->
    <appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
        <file>logs/langchain4j-app.log</file>
        <rollingPolicy class="ch.qos.logback.core.rolling.TimeBasedRollingPolicy">
            <fileNamePattern>logs/langchain4j-app.%d{yyyy-MM-dd}.log.gz</fileNamePattern>
            <maxHistory>30</maxHistory>
            <totalSizeCap>10GB</totalSizeCap>
        </rollingPolicy>
        <encoder>
            <pattern>%d{ISO8601} [%thread] %-5level %logger{36} - %msg%n</pattern>
        </encoder>
    </appender>

    <!-- dev 环境:DEBUG 级别 + 仅控制台 -->
    <springProfile name="dev">
        <logger name="dev.langchain4j" level="DEBUG"/>
        <root level="INFO">
            <appender-ref ref="CONSOLE"/>
        </root>
    </springProfile>

    <!-- prod 环境:INFO 级别 + 文件 + 脱敏 -->
    <springProfile name="prod">
        <logger name="dev.langchain4j" level="INFO"/>
        <root level="INFO">
            <appender-ref ref="CONSOLE"/>
            <appender-ref ref="FILE"/>
        </root>
    </springProfile>
</configuration>

💡 关键设计: - [traceId=%X{traceId:-}] 读 MDC(Mapped Diagnostic Context)的 traceId,关联分布式链路 - rollingPolicy 每天切割 + gzip 压缩,保留 30 天,总大小 10GB 上限 - springProfile 按环境切换:dev 看 DEBUG,prod 看 INFO + 落盘

6. 实战 Logback 配置(企业级)

生产环境的 Logback 配置要考虑:性能 + 切割 + 脱敏 + MDC + 异步。

6.1 完整配置(Console + File + JSON + 异步)

<!-- src/main/resources/logback.xml -->
<?xml version="1.0" encoding="UTF-8"?>
<configuration>

    <!-- 1️⃣ Console(开发用,人眼读) -->
    <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
        <encoder>
            <pattern>%d{HH:mm:ss.SSS} [%thread] %-5level %logger{36} [traceId=%X{traceId:-}] - %msg%n</pattern>
        </encoder>
    </appender>

    <!-- 2️⃣ 文本文件(给人/grep 用,每天切割) -->
    <appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
        <file>logs/app.log</file>
        <rollingPolicy class="ch.qos.logback.core.rolling.TimeBasedRollingPolicy">
            <fileNamePattern>logs/app.%d{yyyy-MM-dd}.%i.log.gz</fileNamePattern>
            <timeBasedFileNamingAndTriggeringPolicy class="ch.qos.logback.core.rolling.SizeAndTimeBasedFNATP">
                <maxFileSize>100MB</maxFileSize>
            </timeBasedFileNamingAndTriggeringPolicy>
            <maxHistory>30</maxHistory>
            <totalSizeCap>20GB</totalSizeCap>
        </rollingPolicy>
        <encoder>
            <pattern>%d{ISO8601} [%thread] %-5level %logger{36} [traceId=%X{traceId:-}] - %msg%n</pattern>
        </encoder>
    </appender>

    <!-- 3️⃣ JSON 文件(给 ELK/Loki/Splunk 收集) -->
    <appender name="JSON_FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
        <file>logs/app.json</file>
        <rollingPolicy class="ch.qos.logback.core.rolling.TimeBasedRollingPolicy">
            <fileNamePattern>logs/app.%d{yyyy-MM-dd}.json.gz</fileNamePattern>
            <maxHistory>30</maxHistory>
        </rollingPolicy>
        <encoder class="ch.qos.logback.classic.encoder.JsonEncoder">
            <includeMdcKeyName>traceId</includeMdcKeyName>
            <includeMdcKeyName>userId</includeMdcKeyName>
            <includeContext>false</includeContext>
        </encoder>
    </appender>

    <!-- 4️⃣ 异步包装器(性能:不阻塞业务线程) -->
    <appender name="ASYNC_FILE" class="ch.qos.logback.classic.AsyncAppender">
        <queueSize>2048</queueSize>
        <discardingThreshold>0</discardingThreshold>
        <neverBlock>false</neverBlock>
        <includeCallerData>false</includeCallerData>
        <appender-ref ref="FILE"/>
        <appender-ref ref="JSON_FILE"/>
    </appender>

    <!-- Logger 级别 -->
    <logger name="dev.langchain4j" level="INFO"/>
    <logger name="dev.langchain4j.model.openai" level="DEBUG"/>  <!-- 想看 prompt 内容就开 -->

    <!-- 抑制一些噪音 logger -->
    <logger name="okhttp3" level="WARN"/>
    <logger name="io.netty" level="WARN"/>

    <root level="INFO">
        <appender-ref ref="CONSOLE"/>
        <appender-ref ref="ASYNC_FILE"/>
    </root>
</configuration>

核心设计点:

  • 双格式输出:文本给人看(app.log)+ JSON 给日志系统吃(app.json)
  • 大小 + 时间双维度切割:每天一个文件,单个最大 100MB
  • 异步 Appender:AsyncAppender 队列 2048,业务线程不阻塞
  • MDC 透出:traceId / userId 进 JSON 字段,方便 ELK 关联
  • 噪音抑制:okhttp / netty 调到 WARN,减少无关注入

7. 敏感信息脱敏

⚠️ 生产环境必做:日志里看到明文 API key / 用户手机号 / 身份证 = 数据泄露事故。

7.1 LangChain4j 自带的脱敏

LangChain4j 1.1+ 提供 SanitizedResponseLoggingAdapter(部分版本),自动把 api-key 字段替换成 api-key=***:

// 部分版本支持
OpenAiChatModel model = OpenAiChatModel.builder()
    .apiKey(System.getenv("OPENAI_API_KEY"))
    .logRequests(true)
    .logResponses(true)
    // .sanitizeResponseLogs(true)  // 视版本支持
    .build();

7.2 自定义 MaskingPatternLayout(企业级)

如果内置脱敏不够(要脱手机号、身份证、银行卡),写自定义 Logback PatternLayout:

// 1️⃣ 自定义 MaskingLayout.java
public class MaskingLayout extends PatternLayout {
    // 匹配 API key (sk-xxx, AKIAxxx)
    private static final Pattern API_KEY_PATTERN = Pattern.compile("(sk-[a-zA-Z0-9]{20,}|AKIA[A-Z0-9]{16})");
    // 匹配中国大陆手机号
    private static final Pattern PHONE_PATTERN = Pattern.compile("(?<!\\d)1[3-9]\\d{9}(?!\\d)");
    // 匹配身份证
    private static final Pattern ID_CARD_PATTERN = Pattern.compile("\\d{17}[\\dXx]");
    // 匹配银行卡(16-19 位数字)
    private static final Pattern BANK_CARD_PATTERN = Pattern.compile("\\b\\d{16,19}\\b");

    @Override
    public String doLayout(ILoggingEvent event) {
        String message = super.doLayout(event);
        return mask(message);
    }

    private String mask(String message) {
        if (message == null) return null;
        message = API_KEY_PATTERN.matcher(message).replaceAll("***MASKED_API_KEY***");
        message = PHONE_PATTERN.matcher(message).replaceAll("***MASKED_PHONE***");
        message = ID_CARD_PATTERN.matcher(message).replaceAll("***MASKED_ID_CARD***");
        message = BANK_CARD_PATTERN.matcher(message).replaceAll("***MASKED_BANK_CARD***");
        return message;
    }
}

2️⃣ 注册到 Logback(logback.xml 加 layout 标签):

<appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
    <!-- 用自定义脱敏 Layout -->
    <layout class="com.yourcompany.logging.MaskingLayout">
        <pattern>%d{HH:mm:ss.SSS} [%thread] %-5level %logger{36} - %msg%n</pattern>
    </layout>
</appender>

效果:

// 原始日志
14:32:01 Request: api-key=sk-proj-abc123def456ghi789jkl, user phone 13812345678

// 脱敏后
14:32:01 Request: api-key=***MASKED_API_KEY***, user phone ***MASKED_PHONE***

7.3 MDC 链路追踪

MDC(Mapped Diagnostic Context) = 把"上下文信息"塞进日志里。最常用的:traceId(分布式链路 ID)。

// 在 Spring Boot 拦截器里塞 traceId
@Component
public class TraceIdInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse resp, Object handler) {
        String traceId = UUID.randomUUID().toString().replace("-", "");
        MDC.put("traceId", traceId);
        MDC.put("userId", getCurrentUserId());  // 当前登录用户
        resp.setHeader("X-Trace-Id", traceId);   // 返回给前端
        return true;
    }

    @Override
    public void afterCompletion(...) {
        MDC.clear();  // 清理,防线程复用污染
    }
}

Logback pattern 里读 MDC:

<pattern>%d{HH:mm:ss.SSS} [traceId=%X{traceId:-NONE}] [user=%X{userId:-GUEST}] %-5level - %msg%n</pattern>

效果:同一次请求的所有日志自动带 traceId,grep 一个 ID 就找到整个调用链。

14:32:01.123 [traceId=a1b2c3d4] [user=user-789] INFO  - 收到 chat 请求
14:32:01.234 [traceId=a1b2c3d4] [user=user-789] DEBUG dev.langchain4j - Request: ...
14:32:03.456 [traceId=a1b2c3d4] [user=user-789] DEBUG dev.langchain4j - Response: ...
14:32:03.567 [traceId=a1b2c3d4] [user=user-789] INFO  - 返回结果,耗时 2.4s

8. 选型决策树

9. 5 个避坑

⚠️ 坑 1:开了 logRequests 但看不见 prompt 内容
症状:logRequests=true 配了,Console 看不到 prompt,只看到一行 "Request sent"。
根因:LangChain4j 的请求日志是 DEBUG 级别,但你 logback 把 dev.langchain4j 设到 INFO。
修法:logging.level.dev.langchain4j=DEBUG(或 <logger name="dev.langchain4j" level="DEBUG"/>)。
⚠️ 坑 2:日志里直接看到明文 API key
症状:日志文件里 api-key=sk-proj-abc123... 明文打印,被爬虫抓到或者审计不合规。
根因:LangChain4j 默认日志输出包含 Authorization header(即 API key)。
修法:用第 7 节自定义 MaskingLayout,匹配 sk-[a-zA-Z0-9]{20,} 正则替换。
⚠️ 坑 3:AsyncAppender 日志丢失
症状:业务跑了 1 小时,日志文件少了 20% 内容。
根因:JVM 关闭时 AsyncAppender 队列里的日志还没刷盘,直接被丢掉。
修法:discardingThreshold=0(永不丢)+ shutdownHook 注册 LoggerFactory.getILoggerFactory() 的 stop。
⚠️ 坑 4:Quarkus 项目用 logback.xml 不生效
症状:在 resources/logback.xml 写了配置,Quarkus 启动完全没读。
根因:Quarkus 用 JBoss LogManager,不用 Logback(除非显式加 quarkus-logging-logback 扩展)。
修法:要么继续用 Quarkus 自家的 quarkus.log.* 配置;要么加 <dependency> <groupId>io.quarkus</groupId> <artifactId>quarkus-logging-logback</artifactId> </dependency>。
⚠️ 坑 5:MDC 线程复用导致 traceId 串了
症状:用户 A 的请求日志里出现用户 B 的 traceId,链路查询彻底乱掉。
根因:Tomcat 线程池复用线程,MDC.clear() 没在请求结束时调用,上一个请求的 traceId 留到了下一个请求。
修法:用 HandlerInterceptor + MDC.clear() + 或者用 Spring 的 MDCContextFilter(Sleuth 自带)。
口诀:脱敏不做等于裸奔,异步不开等于卡死,MDC 不清等于串号,切割不配等于爆盘,DEBUG 不开等于盲飞。

11. 本章小结

  • 3 个开关:logRequests / logResponses / logRequestsAndResponses,生产必开
  • 3 套集成:纯 Java(Builder)/ Spring Boot(properties + logback-spring.xml)/ Quarkus(quarkus.log.*)
  • SLF4J 门面:LangChain4j 只认 SLF4J,后端可换 Logback / Log4j2 / JBoss LogManager
  • 生产五件套:开启开关 + Logback 双格式 + MDC traceId + MaskingLayout 脱敏 + AsyncAppender 异步
  • DEBUG 级别:看 prompt/response 必须开 dev.langchain4j DEBUG,否则只看到 "Request sent" 一行
