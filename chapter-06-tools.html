Function Calling · LLM 调你的 Java 方法

06Tools(函数调用)

LLM 不直接调你的代码。它只"表达意图"(I want to call sum(3, 5)),你的 Java 程序实际执行,把结果塞回对话。@Tool 注解 + ToolSpecification 让这件事零样板。

一句话定性:@Tool 注解让普通 Java 方法变成 LLM 可调用的"工具"。LangChain4j 自动从方法签名生成 JSON Schema 发给模型,模型决定调不调,LangChain4j 自动执行并回传结果。

1. 业务场景

老板:"我们 AI 客服要知道当前时间和订单状态,这两件事 LLM 不会,得让它能调我们 Java 系统的接口。"

解法:把这两个能力写成本地方法 + @Tool 注解 → LLM 看到工具清单 → 遇到相关问题自动决定调哪个 → 你执行工具 → 结果回给 LLM → LLM 用结果回答用户。

3 个真实场景

  • AI 客服查订单 — 工具 = 查订单 API,LLM 决定要不要查
  • AI 助手发邮件 — 工具 = 邮件服务,LLM 决定什么时候发
  • AI 做数学题 — 工具 = 计算器,LLM 不擅长算术,工具补足

2. 极简调用(3 行工具)

经典 Calculator 案例 — 让 LLM 解决 475695037565 的平方根(它自己算会错):

class Calculator {
    @Tool("Sums 2 given numbers")
    double sum(double a, double b) {
        return a + b;
    }

    @Tool("Returns a square root of a given number")
    double squareRoot(double x) {
        return Math.sqrt(x);
    }
}

Assistant assistant = AiServices.builder(Assistant.class)
        .chatModel(model)
        .tools(new Calculator())    // 一行接入工具!
        .build();

String answer = assistant.chat("What is the square root of 475695037565?");

3. 工具调用 4 步循环

4. @Tool 注解完整签名

public @interface Tool {
    String name() default "";                  // 工具名(默认方法名)
    String value() default "";                 // 工具描述(给 LLM 看,重要!)
    String[] aliases() default {};             // 工具别名
    ReturnBehavior returnBehavior() default ReturnBehavior.TO_LLM;
    ToolSearchBehavior searchBehavior() default ...;  // 实验:工具搜索
}

5. @P 注解 4 个字段

工具方法参数上的 @P:

public @interface P {
    String value() default "";     // 描述(简写)
    String name() default "";      // 参数名(覆盖反射名)
    boolean required() default true;  // 是否必填
    String defaultValue() default "";  // 默认值(LLM 漏传时用)
}

3 个典型用法

@Tool("Get current weather")
String getWeather(
    @P("The city name") String city,
    @P(name = "unit", value = "Temperature unit (C/F)", defaultValue = "C") String unit
) { . . . }

⚠️ 编译参数警告:Java 反射读不到真实参数名,只会看到 arg0 arg1。LLM 看到 arg0 完全懵。永远显式写 @P("描述") 或加 @P(name = "city")。或编译时加 -parameters(Maven 加 <parameters>true</parameters>)。

6. 4 种工具定义方式

方式适用代码量
@Tool 注解(AI Service)99% 场景最少
ToolSpecification 手动动态配置 / 跨语言中等
ToolProvider 动态运行时按需注入多
AiServiceToolspec + executor 解耦多

7. 实战:Router Agent(AI 嵌套 AI)

LangChain4j 杀手级特性 —— 一个 AI Service 可以作为另一个 AI Service 的工具:

// 3 个专家服务
interface MedicalExpert { String answer(String q); }
interface LegalExpert   { String answer(String q); }
interface TechnicalExpert { String answer(String q); }

// 路由器:判断问题类型,转发给对应专家
interface RouterAgent {
    @UserMessage("""
        分析用户请求,归类为 'legal' / 'medical' / 'technical',
        然后原样转发给对应的专家。最后返回专家的回答。
        """)
    String route(String userRequest);
}

MedicalExpert medical = AiServices.builder(MedicalExpert.class).chatModel(model).build();
LegalExpert   legal   = AiServices.builder(LegalExpert.class).chatModel(model).build();
TechnicalExpert tech = AiServices.builder(TechnicalExpert.class).chatModel(model).build();

RouterAgent router = AiServices.builder(RouterAgent.class)
        .chatModel(model)
        .tools(medical, legal, tech)   // 3 个 AI Service 当工具
        .build();

8. 工具继承 + 多态

class BaseMathTools {
    @Tool("Calculates the sum of two numbers")
    int sum(int a, int b) { return a + b; }
}

class AdvancedMathTools extends BaseMathTools {
    @Tool("Calculates the product of two numbers")
    int multiply(int a, int b) { return a * b; }
}

// AdvancedMathTools 自动继承 sum,可以同时调 2 个工具
AiServices.builder(MathGenius.class).chatModel(model).tools(new AdvancedMathTools()).build();

9. 错误处理 3 套

LLM 调用工具有 3 种可能出错,LangChain4j 都有对应 handler:

  • 幻觉调用 — 调了一个不存在的工具名 → hallucinatedToolNameStrategy(...)
  • 参数错误 — LLM 传了类型不匹配的值 → toolArgumentsErrorHandler(...)
  • 执行异常 — 工具内部抛异常 → toolExecutionErrorHandler(...)
// 推荐:让 LLM 自纠错(把错误信息回传 LLM,让它重试)
AiServices.builder(Assistant.class)
    .chatModel(model)
    .tools(tools)
    .toolArgumentsErrorHandler((error, ctx) ->
        ToolErrorHandlerResult.text(error.getMessage()))   // 错误信息回传 LLM
    .build();

⚠️ 安全警告:生产不要把原始异常信息回传 LLM!异常里可能有堆栈、文件路径、凭据、PII。一旦流到 LLM = 进了模型日志/响应/可观测管道。回传通用消息(如 "Tool execution failed."),细节走你自己的日志。

11. 避坑指南

坑 1 · 工具描述太模糊 = LLM 不调

LLM 决定调不调用、传什么参数,全靠 @Tool("...") 里的描述。"sum" 描述成 "math" 太模糊 → 模型犹豫。写具体:"Calculates the sum of two given integers and returns the result"。经验:如果一个人类读不懂这个工具干嘛,LLM 也读不懂。

坑 2 · 并行工具调用 = 状态竞争

如果 LLM 一次决定调 2 个工具,默认是顺序执行。要并发必须显式 executeToolsConcurrently()。但并发工具如果改同一个状态(数据库、全局变量) = 数据竞争。慎用。

坑 3 · required=false 不强制,LLM 仍可漏传

required=false 只是把参数从 schema 的 required 数组建议性移除,LLM 仍可能漏。1.x 版本:基本类型漏了 = ToolArgumentsErrorHandler 兜底;对象类型漏了 = 直接传 null(静默 NPE 高发)。

坑 4 · 工具方法不能有太多重载同名

子类重写父类方法 + 同名不同参(overload 而非 override)= LangChain4j 都发现,工具名默认是方法名 = 冲突。必须至少其中一个显式给 name = "..."。

坑 5 · void 返回 ≠ 没返回值

工具方法 void → LangChain4j 自动给 LLM 塞字符串 "Success"。这可能误导 LLM 以为有结果。如果你不想误导,改成 String 返回明确的 "done" 之类。
