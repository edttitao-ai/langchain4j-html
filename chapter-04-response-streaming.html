04Response Streaming(响应流式)

LLM 一个 token 一个 token 吐。等全生成完再返回,用户要等 5-10 秒。StreamingChatModel + StreamingChatResponseHandler 让你逐 token 回调,前端能"打字机"实时显示。

一句话定性:StreamingChatModel 是 ChatModel 的"流式兄弟",API 几乎一样,只是返回用 StreamingChatResponseHandler 回调而不是字符串。适合"长答案 + 实时展示"场景。

1. 业务场景

老板:"为什么我的 AI 客服每次回答都要等 8 秒才出?用户都跑了。"

根因:你用的是 chatModel.chat(msg),整段生成完才返回。但 LLM 实际是 token-by-token 输出的,前 200ms 第一个字就出来了。

流式方案:换 StreamingChatModel,每出一个 token 就立刻推到前端,用户看到的是"打字机效果",感知延迟从 8 秒变成 200ms。

3 个真实场景

  • AI 客服实时回复 — 用户问完不用干等,模型"边想边写"
  • 长文写作助手 — 写 2000 字营销文案,逐段显示不焦虑
  • 代码生成 — Copilot 类工具,逐 token 推送到 IDE 编辑器

3. 极简调用(打字机效果)

完整版 StreamingChatResponseHandler + 4 个 default 回调:

StreamingChatModel model = OpenAiStreamingChatModel.builder()
        .apiKey(System.getenv("OPENAI_API_KEY"))
        .modelName("gpt-4o-mini")
        .build();

String userMessage = "Tell me a joke";
model.chat(userMessage, new StreamingChatResponseHandler() {
    @Override
    public void onPartialResponse(String partialResponse) {
        System.out.print(partialResponse);   // 每个 token 立即打印
    }
    @Override
    public void onCompleteResponse(ChatResponse completeResponse) {
        System.out.println("\n[done]");
    }
    @Override
    public void onError(Throwable error) {
        error.printStackTrace();
    }
});

4. Lambda 简化版(3 行)

99% 场景只需要"打印 token",用官方提供的 lambda 静态方法:

import static dev.langchain4j.model.LambdaStreamingResponseHandler.*;

// 只关心 token:3 行解决
model.chat("Tell me a joke", onPartialResponse(System.out::print));

想同时处理错误:

// onPartialResponseAndError:2 个回调,partialResponse + error
model.chat("Tell me a joke",
    onPartialResponseAndError(
        System.out::print,           // token 回调
        Throwable::printStackTrace  // 异常回调
    ));

5. StreamingChatResponseHandler 完整签名

官方接口有 4 个 default 方法,按触发顺序:

public interface StreamingChatResponseHandler {
    // 1. 每来一个 token 调一次(简单版)
    default void onPartialResponse(String partialResponse) {}

    // 2. 每来一个 token 调一次(带上下文,可取消)
    default void onPartialResponse(PartialResponse partialResponse,
                                    PartialResponseContext context) {}

    // 3. 模型的"思考过程"(o1 / deepseek-r1 这类推理模型)
    default void onPartialThinking(PartialThinking partialThinking) {}

    // 4. 完整响应生成完调一次(带元数据:token 用量、finishReason)
    default void onCompleteResponse(ChatResponse completeResponse) {}

    // 5. 出错时调
    default void onError(Throwable error) {}
}

6. 取消流式(用户中途说"算了")

用户看到一半想停?用 PartialResponseContext.streamingHandle().cancel():

model.chat(userMessage, new StreamingChatResponseHandler() {
    @Override
    public void onPartialResponse(PartialResponse partial,
                                    PartialResponseContext ctx) {
        process(partial);
        if (shouldCancel()) {
            ctx.streamingHandle().cancel();   // 主动断开 HTTP 连接
        }
    }
});

💡 实战技巧:Web 项目里常把"取消"绑到用户点击"停止"按钮。前端发个 signal,后端调 cancel(),立刻断流 + 释放 token 计费。

7. 实战:Spring Boot SSE 推送

最常见的"前端打字机"实现 — Spring Boot + Server-Sent Events:

@GetMapping(value="/chat/stream", produces=MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter stream(@RequestParam String msg) {
    SseEmitter emitter = new SseEmitter(Long.MAX_VALUE);

    streamingModel.chat(msg, new StreamingChatResponseHandler() {
        @Override
        public void onPartialResponse(String token) {
            try { emitter.send(SseEmitter.EventBuilder()
                .data(token).build()); }
            catch (IOException e) { emitter.completeWithError(e); }
        }
        @Override
        public void onCompleteResponse(ChatResponse r) { emitter.complete(); }
        @Override
        public void onError(Throwable e) { emitter.completeWithError(e); }
    });
    return emitter;
}

9. 避坑指南

坑 1 · 流式不是"快",是"看起来快"

流式输出的总耗时和普通调用一样(甚至略高,因为要频繁回调)。它的价值是"用户感知延迟"从 8 秒变成 200ms。如果你后端批处理,流式没意义。

坑 2 · token 回调里别做重操作

onPartialResponse 一次响应可能被调 几十到几百次(每个 token 一次)。在里面查 DB / 发 HTTP / 写日志 = 性能灾难。应该只做"转发到 SSE / 累加 buffer"这种轻活。

坑 3 · 流式是 HTTP 长连接,容易超时

前端 SSE 客户端默认 30s/60s 心跳超时。要在 SseEmitter 里设长 timeout,或者后端定期发心跳(空 comment 帧)保活。

坑 4 · onError 必须实现,否则异常"消失"

StreamingChatResponseHandler 的 onError 是 default 空实现。如果不重写,模型报错时你什么都不知道,前端会一直"打字"到客户端超时。永远至少重写 onError 打个日志。

坑 5 · 部分模型不支持流式

比如老的 gpt-3.5-turbo-instruct(completion 接口)、某些本地 Ollama 小模型。用之前先查厂商文档有没有 streaming 端点,没有就老老实实用普通 chat。
