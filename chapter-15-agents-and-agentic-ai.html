1. 业务场景

老板:"我们客服 AI 什么都答不好 —— 客户问退换政策,AI 答错条款;问物流,AI 编单号;问商品质量,AI 给出 2023 年的旧评测。能不能让 AI 专人专岗?"

❌ 单 AI 死循环(一个万能 Agent 什么都干,什么都干不好):

用户:我买的 NF0A7RKA 雪地手套有质量问题,要退货
AI:  好的,我帮您处理。请问您的订单号是?
用户:订单 #20260615-A
AI:  您的订单金额是 ¥789,我们支持 7 天无理由退货。
     ↑ (AI 不知道是 15 天,而且没查真实订单就瞎编)

用户:那这个手套材质是什么?
AI:  雪地手套通常使用防水尼龙 + 抓绒内里。
     ↑ (AI 在猜,不是查产品库)

用户:寄回地址给我?
AI:  退货地址:广州市天河区 XX 路 XX 号。
     ↑ (AI 给了个假地址!客户真寄过去了,丢件!)

用户:物流单号啥时候发?
AI:  我们会在 24 小时内审核,通过后给您物流单号。
     ↑ (答非所问,而且超时也不知道)

[事故]:客户按假地址寄件 → 丢件 → 平台投诉 → 店群封号 7 天
       ↑ 单 Agent 幻觉 + 角色混乱 + 没有 SOP

✅ 多 Agent 分工(每 Agent 一个职责,通过 AgenticScope 协作):

用户:我买的 NF0A7RKA 雪地手套有质量问题,要退货

[Sequential Workflow 启动]
  ① OrderAgent        → 查订单 #20260615-A (2026-06-15 下单, 6 天)
                        → 写入 scope: orderAmount=¥789, daysSinceOrder=6
  ② PolicyAgent       → 查退换政策(读 scope: 6 天 < 15 天,可退)
                        → 写入 scope: canReturn=true, returnDays=15
  ③ ProductAgent      → 查商品库(scope: orderId → 真实材质/退货地址)
                        → 写入 scope: material="防水尼龙+抓绒",
                                    returnAddress="广州市番禺区 XX 路 XX 号"
  ④ LogisticsAgent    → 物流(scope: 已审批 → 生成真实退货单号)
                        → 写入 scope: trackingNo="YT202606201234"

[Conditional 路由] 政策问题 → PolicyAgent / 物流问题 → LogisticsAgent
[Voting 多模型投票] 质量问题严重性 → 3 个 AI 共识 → 决定退款还是换货

AI:  您的订单 #20260615-A 已查询:
    - 购买日期 2026-06-15,根据 15 天无理由退货政策,
      您在退货期内(剩余 9 天)。
    - 商品材质:防水尼龙 + 抓绒内里。
    - 退货地址:广州市番禺区 XX 路 XX 号(收件人:售后部)。
    - 退货物流单号:YT202606201234(24 小时内揽件)。
用户:麻烦了!
AI:  不客气,如有质量问题需要协助评估,
    我们的质检 Agent 会联系您确认。

🔥 真实成本案例:跨境电商客服单 AI 命中率 60% / 答非所问率 18% / 客户投诉 8% → 平台罚款 ¥5 万/单。多 Agent 分工后命中率 88% / 答非所问 4% / 投诉 1%。月省 ¥18 万(罚款 + 客户挽回 + 培训人力)。

6 个 Agent 能解决的事

  • 📦 跨境选品调研流水线 — Sequential 4 步(选品 → 法规 → 物流 → 报告),每步一个 Agent,质量稳定
  • ✍️ 商品文案多版本生成 — Parallel 3 Agent(高端 / 性价比 / 节日)同时出 3 版,A/B 测试
  • 📞 客服分诊路由 — Conditional 按"法律 / 物流 / 商品"分流到对应专家,精准高效
  • 🏭 批量商品描述生成 — Parallel Mapper 100 SKU 一次性生成,提速 50 倍
  • 🛡️ 多模型投票防幻觉 — Voting 3 个 LLM 共识(高风险退款 / 法规判断),降低误判 80%
  • 👤 退款人工审核 — HITL Agent 决策 → 主管审批,合规要求高金额退款必走人工
口诀:单 LLM 像独行侠(什么都能干,什么都干不好);多 Agent 像专业团队(每人专一,协同完成复杂任务)。企业级复杂任务必须 Agent 化。

2.2 AgenticScope 共享机制

AgenticScope = 多个 Agent 共享的"黑板"。每个 Agent 写自己的 outputKey,下一个 Agent 通过 @V("key") 读对应变量。不用手动传参,自动流转。

// 想象 AgenticScope 是团队白板:

Agent① @Agent(outputKey="story") String generate()
         → 写到白板: story = "龙与巫师的故事..."
                        │
                        ▼
Agent② @Agent String edit(@V("story") String story)
         → 读白板 story,改写 → 写到白板: story = "改写后..."
                        │
                        ▼
Agent③ @Agent String score(@V("story") String story)
         → 读白板 story,打分 → 写到白板: score = 0.85

最终:输出 scope.readState("story")

3. 基础 4 模式(必学)

3.1 Sequential 顺序

用途:流水线处理,A 输出传给 B,B 输出传给 C。

// 3 个 Agent 串行:创作 → 受众编辑 → 风格编辑
CreativeWriter creativeWriter = AgenticServices.agentBuilder(CreativeWriter.class)
    .chatModel(BASE_MODEL)
    .outputKey("story")
    .build();

AudienceEditor audienceEditor = AgenticServices.agentBuilder(AudienceEditor.class)
    .chatModel(BASE_MODEL)
    .outputKey("story")
    .build();

StyleEditor styleEditor = AgenticServices.agentBuilder(StyleEditor.class)
    .chatModel(BASE_MODEL)
    .outputKey("story")
    .build();

// Sequential 编排
NovelCreator novelCreator = AgenticServices.sequenceBuilder(NovelCreator.class)
    .subAgents(creativeWriter, audienceEditor, styleEditor)
    .outputKey("story")
    .build();

String story = novelCreator.createNovel("dragons and wizards", "young adults", "fantasy");
// 3 步顺序执行,每步把 outputKey="story" 写入 scope,下一步读取

3.2 Loop 循环

用途:迭代优化直到达标(打分 + 修改 + 再打分 + 再修改)。

// 评分 Agent(给故事打分)
StyleScorer styleScorer = AgenticServices.agentBuilder(StyleScorer.class)
    .chatModel(BASE_MODEL)
    .outputKey("score")  // 写到 scope: score = 0.85
    .build();

// Loop:评分 → 修改 → 评分 → 修改 ... 直到 score >= 0.8 或 5 次
UntypedAgent styleReviewLoop = AgenticServices.loopBuilder()
    .subAgents(styleScorer, styleEditor)
    .maxIterations(5)
    .exitCondition(scope -> scope.readState("score", 0.0) >= 0.8)
    .build();

// 组合:创作 → 评分-修改循环
StyledWriter styledWriter = AgenticServices.sequenceBuilder(StyledWriter.class)
    .subAgents(creativeWriter, styleReviewLoop)
    .outputKey("story")
    .build();
💡 退出条件:exitCondition(Predicate<AgenticScope>) 默认每次 invoke 都判断一次。testExitAtLoopEnd(true) 强制每轮跑完再判断。exitCondition(BiPredicate<AgenticScope, Integer>) 还能拿到 loop 计数器。

3.3 Parallel 并行

用途:多个独立 Agent 同时跑,合并结果。

// 美食专家 + 电影专家同时跑
FoodExpert foodExpert = AgenticServices.agentBuilder(FoodExpert.class)
    .chatModel(BASE_MODEL)
    .outputKey("meals")
    .build();

MovieExpert movieExpert = AgenticServices.agentBuilder(MovieExpert.class)
    .chatModel(BASE_MODEL)
    .outputKey("movies")
    .build();

// Parallel:两者并发,output 函数合并结果
EveningPlannerAgent planner = AgenticServices.parallelBuilder(EveningPlannerAgent.class)
    .subAgents(foodExpert, movieExpert)
    .executor(Executors.newFixedThreadPool(2))  // 自定义线程池
    .outputKey("plans")
    .output(scope -> {
        List<String> movies = scope.readState("movies", List.of());
        List<String> meals = scope.readState("meals", List.of());
        // 合并:1 电影 + 1 餐
        List<EveningPlan> plans = new ArrayList<>();
        for (int i = 0; i < Math.min(movies.size(), meals.size()); i++) {
            plans.add(new EveningPlan(movies.get(i), meals.get(i)));
        }
        return plans;
    })
    .build();

List<EveningPlan> plans = planner.plan("romantic");

3.4 Parallel Mapper 批处理

用途:同一 Agent 在不同数据上并发(100 SKU 同时生成描述)。

// 给 1 个 Person 生成星座运势
PersonAstrologyAgent astrologyAgent = AgenticServices.agentBuilder(PersonAstrologyAgent.class)
    .chatModel(BASE_MODEL)
    .outputKey("horoscope")
    .build();

// Mapper:批量处理 100 个人,每个独立并发
BatchHoroscopeAgent batchAgent = AgenticServices.parallelMapperBuilder(BatchHoroscopeAgent.class)
    .subAgents(astrologyAgent)
    .itemsProvider("persons")   // 从 scope 读 persons 集合
    .executor(Executors.newFixedThreadPool(3))
    .build();

List<Person> persons = List.of(
    new Person("Mario", "aries"),
    new Person("Luigi", "pisces"),
    new Person("Peach", "leo")
);
List<String> horoscopes = batchAgent.generateHoroscopes(persons);
// 3 个 Person 并发处理,结果自动汇总为 List<String>
⚠️ Mapper 限制:子 Agent 不能配 ChatMemory(每次独立调用,记忆会冲突)。需要持久化对话用 Sequential。

4. 进阶 4 模式

4.1 Conditional 条件路由

用途:先分类,再按类别路由到对应专家。

// 路由器 Agent(分类用户请求)
CategoryRouter router = AgenticServices.agentBuilder(CategoryRouter.class)
    .chatModel(BASE_MODEL)
    .outputKey("category")  // LEGAL / MEDICAL / TECHNICAL / UNKNOWN
    .build();

MedicalExpert medicalExpert = AgenticServices.agentBuilder(MedicalExpert.class)
    .chatModel(BASE_MODEL)
    .outputKey("response")
    .build();

LegalExpert legalExpert = AgenticServices.agentBuilder(LegalExpert.class)
    .chatModel(BASE_MODEL)
    .outputKey("response")
    .build();

// Conditional:按 category 路由到对应专家
UntypedAgent expertsAgent = AgenticServices.conditionalBuilder()
    .subAgents(scope -> scope.readState("category", RequestCategory.UNKNOWN) == RequestCategory.MEDICAL,
               medicalExpert)
    .subAgents(scope -> scope.readState("category", RequestCategory.UNKNOWN) == RequestCategory.LEGAL,
               legalExpert)
    .subAgents(scope -> scope.readState("category", RequestCategory.UNKNOWN) == RequestCategory.TECHNICAL,
               technicalExpert)
    .build();

// 组合:Router → Conditional
ExpertRouterAgent expertRouter = AgenticServices.sequenceBuilder(ExpertRouterAgent.class)
    .subAgents(router, expertsAgent)
    .outputKey("response")
    .build();

String response = expertRouter.ask("I broke my leg, what should I do?");
// → router: MEDICAL → medicalExpert 接管

4.2 Supervisor 监督决策

用途:让 LLM 自己决定调哪些子 Agent(动态决策)。

// 3 个银行 Agent
WithdrawAgent withdraw = AgenticServices.agentBuilder(WithdrawAgent.class)
    .chatModel(BASE_MODEL)
    .build();
CreditAgent credit = AgenticServices.agentBuilder(CreditAgent.class)
    .chatModel(BASE_MODEL)
    .build();
ExchangeAgent exchange = AgenticServices.agentBuilder(ExchangeAgent.class)
    .chatModel(BASE_MODEL)
    .build();

// Supervisor:LLM 自动决定调用顺序
SupervisorAgent bankSupervisor = AgenticServices.supervisorBuilder()
    .chatModel(PLANNER_MODEL)        // 可以用更强的模型做决策
    .subAgents(withdraw, credit, exchange)
    .responseStrategy(SupervisorResponseStrategy.SUMMARY)  // 返回摘要
    .build();

String result = bankSupervisor.invoke("Transfer 100 EUR from Mario's to Georgios' account");
// Supervisor 内部生成:
//   AgentInvocation{exchange, EUR→USD, amount=100}
//   AgentInvocation{withdraw, user=Mario, amount=115}
//   AgentInvocation{credit, user=Georgios, amount=115}
//   AgentInvocation{done, response=...}

4.3 Supervisor 三种 responseStrategy

策略返回内容适用
LAST(默认)最后一个 Agent 的输出多数场景(用户只关心最终结果)
SUMMARY所有 Agent 操作摘要多步操作(银行转账 / 退款流程)
SCORED额外用评分 Agent 选最合适的质量优先(不确信哪个更好)

4.4 Blackboard 黑板协调

用途:多 Agent 根据数据状态自动激活(类似事件驱动)。

// 医疗诊断:症状提取 → 化验分析 → 药物冲突 → 诊断 → 人工审核
MedicalDiagnostics diagnostics = AgenticServices.plannerBuilder(MedicalDiagnostics.class)
    .subAgents(symptomExtractor, labAnalyzer, drugInteraction, diagnosisAgent, humanReview)
    .planner(() -> new BlackboardPlanner(
        scope -> scope.hasState("approvedDiagnosis"),  // 终止条件
        agentOfType(DrugInteractionChecker.class,
            scope -> scope.readState("symptoms", "").toLowerCase().contains("medication"))
        .or(declarationOrder())   // 其他 Agent 按声明顺序激活
    ))
    .outputKey("approvedDiagnosis")
    .build();
💡 Blackboard 适合:多 Agent 依赖关系复杂、激活条件动态(根据 scope 状态决定下一步)。医疗诊断 / 工业控制 / 多 Agent 协作推理。

4.5 HITL 人工介入

用途:关键决策让人类审批(高金额退款 / 法规风险 / 医疗诊断)。

// 人工审核 Agent:返回修改意见或不修改
HumanInTheLoop humanReview = AgenticServices.humanInTheLoopBuilder()
    .description("Review the diagnosis and approve or request additional analysis")
    .outputKey("symptoms")           // 写入 scope: symptoms(可能被覆盖)
    .inputKey(String.class, "diagnosis")  // 仅在 diagnosis 存在时激活
    .responseProvider(scope -> {
        String diagnosis = scope.readState("diagnosis", "");
        String symptoms = scope.readState("symptoms", "");

        // 弹个对话框给主管审批(实际项目换成 JavaFX / Web)
        boolean approved = showReviewDialogToHuman(diagnosis, symptoms);

        if (!approved) {
            return symptoms + ". Patient also reports blurred vision.";
            // 主管驳回,补充症状,重新激活 DrugInteractionChecker
        }
        scope.writeState("approvedDiagnosis", diagnosis);
        return symptoms;
    })
    .build();

5. Voting 投票模式

用途:3 个 Agent 同时答同一问题,投票降低单 Agent 偏见 / 幻觉。

// 3 个评分 Agent(用不同 prompt / 模型)
QualityScorer gpt4 = AgenticServices.agentBuilder(QualityScorer.class)
    .chatModel(OpenAiChatModel.builder().modelName("gpt-4o").build())
    .outputKey("vote")
    .build();

QualityScorer claude = AgenticServices.agentBuilder(QualityScorer.class)
    .chatModel(AnthropicChatModel.builder().modelName("claude-3-5-sonnet").build())
    .outputKey("vote")
    .build();

QualityScorer qwen = AgenticServices.agentBuilder(QualityScorer.class)
    .chatModel(QwenChatModel.builder().modelName("qwen-max").build())
    .outputKey("vote")
    .build();

// Voting:3 个 Agent 并发,取多数票
ContentModerator moderator = AgenticServices.votingBuilder(ContentModerator.class)
    .subAgents(gpt4, claude, qwen)
    .votingStrategy(VotingStrategy.majority())  // 多数票
    .build();

Verdict verdict = moderator.moderate(userContent);
// 3 个模型同时判断,多数票(2/3 通过 = 通过)

5.1 3 种 VotingStrategy

策略聚合方式适用
VotingStrategy.majority()取出现最多的值分类 / 标签枚举
VotingStrategy.average()数值平均评分 / 置信度
VotingStrategy.highest()取最大值风险评估 / 最乐观
💡 自定义策略:VotingStrategy 是 functional interface,可以写 lambda:
VotingStrategy custom = votes -> /* 自定义加权 / 置信度过滤 / 法定人数 */

6. 异步 + 流式

6.1 Async 异步

用途:Agent 调用立即返回,不等结果(后续 Agent 需要时自动阻塞)。

// 把 Agent 标 async
FoodExpert foodExpert = AgenticServices.agentBuilder(FoodExpert.class)
    .chatModel(BASE_MODEL)
    .async(true)               // 异步调用
    .outputKey("meals")
    .build();

// 即使在 Sequential 里,async Agent 也会并发执行
EveningPlannerAgent planner = AgenticServices.sequenceBuilder(EveningPlannerAgent.class)
    .subAgents(foodExpert, movieExpert)  // 两个 async Agent 同时跑
    .executor(Executors.newFixedThreadPool(2))
    .build();

6.2 Streaming 流式

public interface StreamingCreativeWriter {
    @UserMessage("Generate a story about {{topic}}")
    @Agent("Generates a story")
    TokenStream generateStory(@V("topic") String topic);
}

StreamingCreativeWriter writer = AgenticServices.agentBuilder(StreamingCreativeWriter.class)
    .streamingChatModel(streamingBaseModel())   // 用 StreamingChatModel
    .outputKey("story")
    .build();

TokenStream tokenStream = writer.generateStory("dragons and wizards");
// 边生成边推送,适合长内容
⚠️ 流式限制:Streaming Agent 在工作流里,只有最外层能流式(内部的 TokenStream 会被吞掉等待完整)。需要嵌套流式用 Supervisor + 多 Streaming Agent。

7. 8 模式选型决策

业务场景 → 选哪种模式:

业务场景推荐模式理由
多步流水线(选品 → 法规 → 报告)Sequential严格顺序,每步依赖上一步
迭代优化(文案打分 + 修改)Loop直到达标退出
多版本同时生成Parallel独立任务,合并结果
批量处理(100 SKU 一次性)Parallel Mapper同 Agent 在集合上 fan-out
客服分诊(按类别路由)Conditional分类后选专家
复杂决策(LLM 自己编排)Supervisor步骤不确定,LLM 动态决定
事件驱动多 Agent 协作Blackboard按数据状态激活
关键决策需人工HITL合规 / 高风险
降低单模型偏见Voting多模型共识

组合拳(实战经常多个模式嵌套):

  • Sequential + Parallel:流水线每一步又并发出多版本(如选品 → 多平台描述生成)
  • Sequential + Conditional:路由 + 流水线(如客服分流 → 后续流水线)
  • Supervisor + Sequential:动态决策 + 固定步骤(如银行转账:supervisor 决定用哪些 Agent)
  • Loop + Voting:多模型评分 → 修改循环(评分更稳)

8. AgenticScope 共享机制深挖

AgenticScope 是 Agent 间的"共享内存"。每个 Agent 通过 outputKey 写,通过 @V("key") 或 readState("key") 读。

// 写入:outputKey
CreativeWriter writer = AgenticServices.agentBuilder(CreativeWriter.class)
    .outputKey("story")       // 把返回值写到 scope["story"]
    .build();

// 读取:@V(在方法参数上)
public interface StyleEditor {
    String editStory(@V("story") String story);  // 从 scope 读 "story"
}

// 读取:动态(在 Conditional / Loop 里)
.exitCondition(scope -> scope.readState("score", 0.0) >= 0.8)

// UntypedAgent:不用写接口,直接用 Map
UntypedAgent creator = AgenticServices.sequenceBuilder()
    .subAgents(writer, editor)
    .build();
Map<String, Object> result = creator.invoke(Map.of(
    "topic", "dragons",
    "style", "fantasy"
));
// 输入 map 自动复制到 scope,输出从 scope 读
💡 编译选项:Agent 方法参数名 story 必须运行时保留,需要编译加 -parameters(Maven 加 <parameters>true</parameters>),否则 @V 必填。

9. 10 避坑

坑 1 ❌ 直接当 AI Service 写 Agent

症状:AiServices.builder(MyAgent.class).build() 也能跑,但 AgenticScope 完全没生效,多 Agent 不串数据。
根因:Agent 必须用 AgenticServices 创建,不能用 AiServices。
修法:AgenticServices.agentBuilder(MyAgent.class).outputKey("...").build()。

坑 2 ❌ Loop 没设 maxIterations 死循环

症状:Agent 一直循环不退出,烧光 token。
根因:Loop 默认 maxIterations=10,但 exitCondition 永远不满足就会跑满 10 次;如果忘了设 max,默认无限。
修法:必须同时设 maxIterations(N) + exitCondition(...)。

坑 3 ❌ Supervisor 卡死在 done Agent

症状:Supervisor 调了 3 次都生成"还没完成",循环往复。
根因:Supervisor 需要至少一个 Agent 调完能产 "done" 信号(返回 task complete),prompt 里没明示。
修法:Sub-Agent 的 @UserMessage 加 "If task is complete, return 'done'"。

坑 4 ❌ Parallel Mapper 子 Agent 配了 ChatMemory

症状:IllegalStateException: Memory cannot be used with parallel mapper
根因:Mapper 每个 item 一个独立 Agent,记忆会冲突。
修法:Parallel Mapper 的子 Agent 不能配 ChatMemory。需要记忆用 Sequential。

坑 5 ❌ HITL responseProvider 阻塞线程

症状:HITL 弹对话框卡死整个工作流。
根因:responseProvider 是同步阻塞的,人类不点确定就一直等。
修法:1)对话框必须 timeout(如 30 秒自动 reject);2)提供 reject 默认值;3)异步消息队列(钉钉 / 飞书 审批回调)。

坑 6 ❌ Async Agent 输出格式不一致

症状:foodExpert 返回 List<String>,movieExpert 返回 String,聚合时报 ClassCastException。
根因:Parallel 聚合时类型必须对齐。
修法:同类型 Parallel 子 Agent 用同一 outputType,或在 output(scope) 函数里手动转换。

坑 7 ❌ Blackboard 激活条件太宽,死循环

症状:Blackboard Planner 一直激活 DrugInteractionChecker,循环跑。
根因:agentOfType 的激活条件没限制,scope 每次更新都触发。
修法:激活条件要"仅当数据变化时",加 scope.hasState("symptoms") + !scope.readState("symptoms", "").equals(lastSymptoms)。

坑 8 ❌ Stream Agent 嵌套工作流失效

症状:Sequential 里第一个 Agent 是 Streaming,TokenStream 在工作流里被吞掉,等所有 Agent 跑完才整体返回。
根因:LangChain4j 工作流默认等所有 Agent 完成才返回,流式只能在最外层生效。
修法:要么用最外层 Streaming Agent + 内部 Sequential 同步 Agent,要么 Supervisor 配多 Streaming。

坑 9 ❌ outputKey 冲突覆盖

症状:两个 Agent 都写 outputKey="response",后写的覆盖前写的。
根因:AgenticScope 是 Map,同名 key 直接覆盖。
修法:outputKey 命名要唯一(如 "finalResponse" / "intermediateResponse")。

坑 10 ❌ 忽略模块 experimental 警告

症状:升级 LangChain4j 1.x → 1.y 后,Agent 代码编译失败。
根因:langchain4j-agentic 模块还在实验阶段,API 可能大改。
修法:生产用前 pin 版本;每 3 个月看一次 release notes;准备 fallback(用 Sequential AI Services 手拼)。
