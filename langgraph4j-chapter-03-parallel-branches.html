03 并行分支(fan-out / fan-in + 并发执行)

addParallelNodeExecutor · ForkJoinPool · 3 大限制 · 3 案例 · 多 LLM/检索/工具并发 6 场景

一句话定性:并行节点 = 多个下游节点同时跑(fan-out → fan-in)。LangGraph4j 的并发由图管理(不是节点自己并发),通过 RunnableConfig.addParallelNodeExecutor("nodeId", Executor) 指定哪个节点的下游要并发。默认顺序执行,必须显式配 Executor 才并发。

核心价值:多 LLM 并行评审 / 多 retriever 并行查 / 多工具并发调用 / 多 Agent 协作 —— 节省 wall-clock 时间(不是 CPU,就是让总耗时 = 最慢的那个,而不是 sum)。

1. 业务场景

老板:"咱们的 RAG 查询是串行的 —— 先用关键词检索 → 再用向量检索 → 再用 reranker,3 步加起来 1.2 秒。怎么降到 0.4 秒?"

解法:3 个检索器并行跑(fan-out) → 等全部回来 → 进入 reranker(fan-in)。用 LangGraph4j 并行节点:1 个 root 节点 + 3 个并行子任务。wall-clock 从 1.2s 降到 ~0.4s(3 路并发,瓶颈是最慢那个)。

6 个并行分支能解决的事

  • 🔀 多 RAG 检索器并发 — 关键词 + 向量 + 知识图谱同时查,1.2s → 0.4s
  • 🤖 多 LLM 并行评审 — 3 个不同模型(GPT-4 / Claude / Gemini)对同一 prompt 投票,综合答案
  • 🛠️ 多工具并发调用 — "查订单"+"查库存"+"查物流"3 工具并发,3s → 1.2s
  • 👥 多 Agent 协作 — 多个 Agent 子图并行跑(对应 lg02 子图),最后汇总
  • 🔍 多 Moderation 审查 — 内容审核 / 涉政 / 涉黄 / 暴力 4 路并发审查,1 路失败不影响其他
  • 🌐 多语言翻译并发 — 同一文档并发翻成 5 国语言(5 个翻译 API 同时调),5s → 1.5s

💡 什么时候不需要:单步 / 单工具 / 步骤间有强依赖 / 总耗时 < 100ms —— 并发反而增加复杂度。并发是"多个独立任务 + 节省 wall-clock"的优化方案。

口诀:并发是"图管的",不是"节点自己"。用 addParallelNodeExecutor("A", ForkJoinPool) 告诉图"A 的下游要并发"。⚠️ 必须配 Executor 才并发(否则顺序),必须传 runnableConfig(否则顺序)。3 大限制:叉接 / 单步 / 无条件边。

2. 3 大限制(必读!)

LangGraph4j 并行节点有严格限制,设计为单层 fork-join 模式:

限制说明示意
① 只能叉接1 个 root → N 个并行分支(不允许多层嵌套并发)A → [A1, A2, A3] ✅
② 只允许 1 个并行步骤1 张图只能有1 个 fork 点(不能有 2 个并行的 fork)A → [A1, A2, A3] → A4 ❌(A4 是新 fork)
③ 不允许条件边并行分支的根节点不能用条件边(避免复杂的并发路由)addConditionalEdges("A", ...) ❌

2.1 为什么这么严?

LangGraph4j 当前的并行实现是"轻量 fork-join":

  • 易实现:1 个根 + N 个子节点 + 1 个 join,模型简单
  • 易推理:图的状态可预测
  • 够用:90% 并行需求都是这个模式

多步并行 / 嵌套并行怎么办?用 子图(lg02) —— 把多层并行包成子图,在父图里作为 1 个节点(用子图内部的多步并行)。

3. 基础:定义并行节点

核心是3 步:

  1. 建图:多个节点关联到同一条边 → 自动形成 fork
  2. 配 Executor:addParallelNodeExecutor("A", ForkJoinPool.commonPool())
  3. 执行:必须传 runnableConfig(Executor 在 config 里)

3.1 Hello World 并行

import java.util.concurrent.ForkJoinPool;
import static org.bsc.langgraph4j.StateGraph.*;

var workflow = new MessagesStateGraph<String>()
    .addNode("A",  makeNode("A"))   // 根
    .addNode("A1", makeNode("A1"))  // 并行分支 1
    .addNode("A2", makeNode("A2"))  // 并行分支 2
    .addNode("A3", makeNode("A3"))  // 并行分支 3
    .addNode("B",  makeNode("B"))   // join
    .addNode("C",  makeNode("C"))   // join 之后

    // ← fork:A 完后 A1/A2/A3 同时跑
    .addEdge("A", "A1")
    .addEdge("A", "A2")
    .addEdge("A", "A3")
    // ← join:全部回来才进 B
    .addEdge("A1", "B")
    .addEdge("A2", "B")
    .addEdge("A3", "B")
    .addEdge("B", "C")
    .addEdge(START, "A")
    .addEdge("C", END)
    .compile();

// ⚠️ 关键:配 Executor + 传 runnableConfig
var runnableConfig = RunnableConfig.builder()
    .addParallelNodeExecutor("A", ForkJoinPool.commonPool())  // A 的下游并发
    .build();

var result = workflow.stream(Map.of(), runnableConfig)
    .stream()
    .peek(System.out::println)
    .reduce((a, b) -> b)
    .map(NodeOutput::state);

行为:A 跑完 → A1/A2/A3 同时在 ForkJoinPool.commonPool() 跑 → 全部回来 → 进 B → 进 C → END。

⚠️ 关键 2 点:
  • 必须配 Executor —— 没配 = 顺序执行(A → A1 → A2 → A3 → B,不是并发的)
  • 必须传 runnableConfig —— Executor 存在 config 里,workflow.stream() 不传 config = 用默认顺序

4. join 后用条件边(回环)

并行分支完成后,可以从 join 节点出发用条件边回环(到并行分支里的某个节点):

var workflow = new MessagesStateGraph<String>()
    .addNode("A",  makeNode("A"))
    .addNode("A1", makeNode("A1"))
    .addNode("A2", makeNode("A2"))
    .addNode("A3", makeNode("A3"))
    .addNode("B",  makeNode("B"))
    .addNode("C",  makeNode("C"))
    .addEdge("A", "A1")
    .addEdge("A", "A2")
    .addEdge("A", "A3")
    .addEdge("A1", "B")
    .addEdge("A2", "B")
    .addEdge("A3", "B")
    // .addEdge("B", "C")  // 注释掉直连,改条件
    .addConditionalEdges("B",
        edge_async(state -> state.lastMinus(1)
            .filter(m -> Objects.equals(m, "A3"))
            .map(m -> "continue")
            .orElse("back")),
        EdgeMappings.builder()
            .to("A1", "back")      // 回环到 A1
            .to("C", "continue")
            .build())
    .addEdge(START, "A")
    .addEdge("C", END)
    .compile();

注意:条件边从 B 出发(不是从 A 出发)是允许的 —— 只有"并行根节点"才禁止条件边。

5. 用子图当并行分支(突破单步限制)

问题:每条并行分支只能有 1 个节点,需要多步怎么办?—— 用子图(把多步封装在子图里)。

5.1 混合:节点 + 子图

// A1 / A3 是子图(可多步),A2 是单节点
var subgraphA1 = new MessagesStateGraph<String>()
    .addNode("A1.1", makeNode("A1.1"))
    .addNode("A1.2", makeNode("A1.2"))
    .addEdge(START, "A1.1")
    .addEdge("A1.1", "A1.2")
    .addEdge("A1.2", END)
    .compile();

var subgraphA3 = new MessagesStateGraph<String>()
    .addNode("A3.1", makeNode("A3.1"))
    .addNode("A3.2", makeNode("A3.2"))
    .addEdge(START, "A3.1")
    .addEdge("A3.1", "A3.2")
    .addEdge("A3.2", END)
    .compile();

var workflow = new MessagesStateGraph<String>()
    .addNode("A",  makeNode("A"))
    .addNode("A1", subgraphA1)              // ← 子图
    .addNode("A2", makeNode("A2"))
    .addNode("A3", subgraphA3)              // ← 子图
    .addNode("B",  makeNode("B"))
    .addEdge("A", "A1")
    .addEdge("A", "A2")
    .addEdge("A", "A3")
    .addEdge("A1", "B")
    .addEdge("A2", "B")
    .addEdge("A3", "B")
    .addEdge(START, "A")
    .addEdge("B", END)
    .compile();

// A 的下游(A1 子图 / A2 节点 / A3 子图)都并发
workflow.stream(Map.of(),
    RunnableConfig.builder()
        .addParallelNodeExecutor("A", ForkJoinPool.commonPool())
        .build());

6. 实战:多 RAG 检索器并发

经典场景 —— 关键词 / 向量 / 知识图谱 3 个 retriever 并发查,rerank 后输出:

// === 3 个 retriever 子图 ===
// 关键词检索
var keywordSubgraph = new StateGraph(KeywordState.SCHEMA, KeywordState::new)
    .addNode("search_elastic", node_async(state -> {
        // 调 ES / OpenSearch 关键词查询
        return Map.of("keywordResults", doElasticSearch(state));
    }))
    .addNode("format_hits", node_async(state ->
        Map.of("keywordResults", formatHits(state.value("keywordResults").orElse(List.of())))))
    .addEdge(START, "search_elastic")
    .addEdge("search_elastic", "format_hits")
    .addEdge("format_hits", END)
    .compile();

// 向量检索
var vectorSubgraph = new StateGraph(VectorState.SCHEMA, VectorState::new)
    .addNode("embed_query", node_async(state -> {
        var emb = embeddingModel.embed(state.value("query").orElse("")).content();
        return Map.of("queryEmbedding", emb);
    }))
    .addNode("search_pgvector", node_async(state -> {
        // 调 pgvector 余弦相似度
        return Map.of("vectorResults", doVectorSearch(state));
    }))
    .addEdge(START, "embed_query")
    .addEdge("embed_query", "search_pgvector")
    .addEdge("search_pgvector", END)
    .compile();

// 知识图谱检索
var graphSubgraph = new StateGraph(GraphState.SCHEMA, GraphState::new)
    .addNode("extract_entities", node_async(state -> {
        // NER 提取实体
        return Map.of("entities", extractEntities(state));
    }))
    .addNode("query_neo4j", node_async(state -> {
        // Neo4j Cypher 查询
        return Map.of("graphResults", doNeo4jQuery(state));
    }))
    .addEdge(START, "extract_entities")
    .addEdge("extract_entities", "query_neo4j")
    .addEdge("query_neo4j", END)
    .compile();

// === 主图:3 路并发 → rerank ===
var ragWorkflow = new StateGraph(RagState.SCHEMA, RagState::new)
    .addNode("parse_query",  node_async(state -> Map.of("query", state.value("userQuery").orElse(""))))
    .addNode("keyword",      keywordSubgraph)     // 子图 1
    .addNode("vector",       vectorSubgraph)       // 子图 2
    .addNode("graph",        graphSubgraph)        // 子图 3
    .addNode("rerank",       node_async(state -> {
        // 合并 3 路结果,rerank,取 top-5
        var all = merge3Results(
            state.value("keywordResults").orElse(List.of()),
            state.value("vectorResults").orElse(List.of()),
            state.value("graphResults").orElse(List.of())
        );
        return Map.of("topDocs", rerank(all, 5));
    }))
    .addNode("llm_generate", node_async(state ->
        Map.of("answer", llm.chat(formatContext(state.value("topDocs").orElse(List.of())),
                                    state.value("query").orElse("")))))

    .addEdge(START, "parse_query")
    .addEdge("parse_query", "keyword")
    .addEdge("parse_query", "vector")
    .addEdge("parse_query", "graph")
    .addEdge("keyword",      "rerank")
    .addEdge("vector",       "rerank")
    .addEdge("graph",        "rerank")
    .addEdge("rerank",       "llm_generate")
    .addEdge("llm_generate", END)
    .compile();

// 跑(parse_query 的下游并发)
var config = RunnableConfig.builder()
    .addParallelNodeExecutor("parse_query", ForkJoinPool.commonPool())
    .build();

var result = ragWorkflow.stream(Map.of("userQuery", "LangGraph4j 怎么用?"), config);

性能:

  • 顺序:parse_query(0.1s) + 关键词(0.4s) + 向量(0.5s) + 图谱(0.3s) + rerank(0.2s) + LLM(1s) = 2.5s
  • 并行:parse_query(0.1s) + max(关键词 0.4, 向量 0.5, 图谱 0.3)(0.5s) + rerank(0.2s) + LLM(1s) = 1.8s(节省 0.7s)
  • 3 路全并发瓶颈在 LLM,优化到 LLM 内部流式(对应 lg04)

7. 实战:多 LLM 投票

// 3 个 LLM 并行评审同一 prompt
var gptVote = new MessagesStateGraph<String>()

var geminiVote = new MessagesStateGraph<String>()  // 同样结构,调 Gemini
    .addNode("call_gemini", node_async(state ->

var voteWorkflow = new StateGraph(VoteState.SCHEMA, VoteState::new)

    .addEdge("gemini", "vote")

voteWorkflow.stream(Map.of("question", "What is 2+2?"),
    RunnableConfig.builder()
        .addParallelNodeExecutor("dispatch", ForkJoinPool.commonPool())
        .build());

wall-clock:1 个 LLM 调用 ~2s,3 个并发 = 2s(而不是 6s)。

8. 决策树(用不用并行?)

9. 5 个避坑

⚠️ 坑 1:不传 runnableConfig,以为在并发
症状:workflow.stream(inputs)(不传 config),看起来节点都跑了,但实际是顺序的,wall-clock = sum 而不是 max。
根因:Executor 在 RunnableConfig 里,没传 config = 用默认顺序执行。
修法:必须用 workflow.stream(inputs, config),config 里有 addParallelNodeExecutor。
⚠️ 坑 2:并行根用了条件边
症状:addConditionalEdges("A", router, mapping) + addEdge("A", "A1") + addEdge("A", "A2") 混用,跑起来报错或行为奇怪。
根因:限制 3:并行根节点不能用条件边(避免复杂并发路由)。
修法:要么把条件判断移到 A 节点内部(返回 State 时决定下一步);要么用子图(lg02)把条件边封装在子图里,父图只看到 1 个节点。
⚠️ 坑 3:试图做 2 个并行的 fork
症状:A → [A1, A2, A3] → A4 → [A4.1, A4.2],跑起来第二个 fork 没并发 / 报错。
根因:限制 2:1 张图只能有 1 个并行步骤。
修法:
  • 方案 1:用子图 —— 把第二层 fork 包成子图,父图只看到 1 节点
  • 方案 2:合并到第一层(A 的下游) —— 重新设计图结构,避免连续 2 层 fork
⚠️ 坑 4:用默认 ForkJoinPool 没改,阻塞 I/O 卡死
症状:并行节点里有阻塞 IO(数据库 / HTTP / 同步 LLM),用 ForkJoinPool.commonPool() 跑,commonPool 线程被占满,其他任务卡死。
根因:commonPool 默认大小 = 机器 CPU 核数 - 1,适合 CPU 密集型,不适合 IO 密集。
修法: 
// ✅ 自定义 Executor:适合 IO 密集
ExecutorService ioPool = Executors.newFixedThreadPool(20, r -> {
    Thread t = new Thread(r, "lg-parallel-io");
    t.setDaemon(true);
    return t;
});

var config = RunnableConfig.builder()
    .addParallelNodeExecutor("A", ioPool)   // ← 不用 commonPool
    .build();
原则:LLM 调用 / 数据库查询 / HTTP 调外部 → 用 固定大小线程池(20-50)。纯计算(数据处理 / 序列化)→ commonPool。
⚠️ 坑 5:并行节点共享 State 写入冲突
症状:3 个并行节点都返回 Map.of("counter", 1),最后 counter 总是 1(而不是 3),数据被覆盖。
根因:State 的 Reducer 决定怎么合并 —— 覆盖 reducer(Channel.of((o, n) -> n))后写覆盖前写,只看到最后一个。
修法:
  • 累加字段(每个并行节点贡献一部分)用 Channels.appender(ArrayList::new)
  • 独立字段(每个节点写自己的 key)用 Channel.of((o, n) -> n)
  • 禁止并行写同一 key(除非用累加 reducer)

11. 本章小结

  • 并发是图管的:用 addParallelNodeExecutor 配 Executor + 必须传 config 才并发
  • 3 大限制:叉接(1→N)/ 单步(1 张图 1 个 fork)/ 无条件边(根不能条件路由)
  • 突破单步:用子图当并行分支(lg02 组合)
  • Executor 选择:CPU 密集用 commonPool,IO 密集用自定义 newFixedThreadPool(20-50)
  • 状态累加:并行写同一 key 用 Channels.appender(否则被覆盖)
  • 5 大场景:多 RAG 检索 / 多 LLM 投票 / 多工具 / 多 Moderation / 多语言翻译
  • 配合 lg04 流式:并行 + 流式 = 实时 + 高性能
一句话总结:LangGraph4j 并行 = "图管并发 + ForkJoinPool + 3 大限制"。默认顺序,配 Executor 才并发。必传 config。多层并行用子图。下一章(lg04 流式传输)让单个 LLM Token 级别边生成边推。
