02 子图(Graph 嵌套 + 模块化 + 多智能体)

3 种添加方式 · 状态共享 · 中断 · 可视化 · 多智能体 / 团队协作 6 场景

一句话定性:子图(Subgraph)= 用作另一个图的节点的图,本质是封装 + 组合。3 种添加方式 —— 已编译子图作为节点(共享状态)/ 作为节点操作(状态转换)/ 作为状态子图合并(深度集成)。

核心价值:LangGraph4j 的子图机制把"大图拆小"做成一级概念 —— 构建多智能体系统(多个 Agent 协作)+ 跨图复用节点(子图在多个父图里跑)+ 团队独立开发(按子图接口集成,互不耦合)。

1. 业务场景

老板:"咱们的 AI 客服主图已经有 30 个节点了 —— 订单处理 / 退换货 / 物流查询 / 发票 / 投诉 5 大模块。新加一个'换货'功能要在主图里加 3 个节点 + 5 条边,每次都改主图。怎么拆?"

解法:用 子图 把 5 大模块拆成独立子图,主图只调 addNode("order_subgraph", orderSubgraph)。新增模块 = 加新子图,主图零改动。多团队协作:订单团队 / 物流团队各管各的子图,只约定输入输出 State key。

6 个子图能解决的事

  • 🧩 大图拆小 — 主图 30 节点 → 1 父图 + 5 子图,每个子图 ≤ 8 节点,复杂度指数级下降
  • 👥 多智能体协作 — "订单 Agent" / "支付 Agent" / "物流 Agent" 各自是子图,主图协调
  • ♻️ 跨图复用 — "用户认证子图"在登录 / 注册 / 改密码 / 注销 4 个父图里都用到,只写一次
  • 🏢 团队独立开发 — 订单团队只管 order_subgraph,物流团队只管 logistics_subgraph,约定 State key 即可
  • 🔌 子图替换 / 升级 — A/B 测试:同一父图,子图 v1 / v2 切换,看哪个效果更好
  • 🧪 子图独立测试 — 子图单独 .compile() 测,不需要把整个父图拉起来

💡 什么时候不需要:图 < 10 节点 / 一次性脚本 / 单团队维护 / 没有"模块"概念 —— 直接平铺写,过度设计反而难维护。子图是"模块边界清晰 + 跨图复用 + 多团队"时的优化方案。

口诀:子图 = 节点的图。3 种添加方式:已编译(共享 state)/ 作为节点操作(状态转换)/ 作为状态子图(深度合并)。默认用第 1 种(已编译子图),需要状态转换用第 2 种,需要深度集成用第 3 种。子图节点 忽略非共享 key(不会污染父图 State)。

2. 3 种添加子图方式

方式API何时用状态共享
① 已编译子图作节点addNode("sub", workflowChild.compile())父图 / 子图共享 state schema共享 key 通信
② 作为节点操作addNode("sub", (state) -> ...stream(subgraph))父图 / 子图状态模式不同,需转换手动转换
③ 作为状态子图addNode("sub", workflowChild)(未编译)父图 / 子图紧密关联,共享所有完全共享

3. 方式 ① 已编译子图作节点(最简单)

前提:父图和子图状态模式至少共享一个 key。如果完全没有共享 key,要用方式 ②(节点操作)。

// 1. 定义子图
var childBuilder = new StateGraph(ChildState.SCHEMA, ChildState::new)
    .addNode("validate", node_async(state -> {
        String input = (String) state.value("input").orElse("");
        return Map.of("valid", !input.isEmpty());
    }))
    .addNode("transform", node_async(state -> {
        String input = (String) state.value("input").orElse("");
        return Map.of("output", input.toUpperCase());
    }))
    .addEdge(START, "validate")
    .addConditionalEdges("validate",
        edge_async(state -> {
            Boolean valid = (Boolean) state.value("valid").orElse(false);
            return valid ? "valid" : "invalid";
        }),
        Map.of(
            "valid", "transform",
            "invalid", END
        ))
    .addEdge("transform", END);

var compiledChild = childBuilder.compile();   // ← 先 compile 子图

// 2. 父图添加子图节点
var parentGraph = new StateGraph(ParentState.SCHEMA, ParentState::new)
    .addNode("subgraph", compiledChild)        // ← 一行:已编译子图作节点
    .addEdge(START, "subgraph")
    .addEdge("subgraph", END)
    .compile();

2 个关键规则:

  • 父图 / 子图至少共享一个 key才能通信(无共享 key → 用方式 ②)
  • 额外 key 被忽略:传给子图的额外 key(非共享)被忽略;子图返回的额外 key(父图没定义)被忽略

4. 方式 ② 作为节点操作(状态转换)

父图 / 子图状态模式完全不同时,用节点函数手动转换:

// 1. 子图(状态模式: input + result)
StateGraph childGraph = new StateGraph(ChildState.SCHEMA, ChildState::new)
    .addNode("substep1", node_async(state -> {
        String input = (String) state.value("input").orElse("");
        return Map.of("result", "SubStep1:" + input);
    }))
    .addNode("substep2", node_async(state -> {
        String prev = (String) state.value("result").orElse("");
        return Map.of("result", prev + "->SubStep2");
    }))
    .addEdge(START, "substep1")
    .addEdge("substep1", "substep2")
    .addEdge("substep2", END);

CompiledGraph compiledChild = childGraph.compile();

// 2. 父图中用 AsyncNodeActionWithConfig 调子图
StateGraph parentGraph = new StateGraph(ParentState.SCHEMA, ParentState::new)
    .addNode("subgraph", (state) -> {
        // 父图状态 → 子图状态
        var input = Map.<String, Object>of(
            "subgraphKey",
            state.lastMessage().orElseThrow()
        );

        // 调子图(stream 是同步的,先消费再拿结果)
        return compiledChild.stream(input)
            .forEachAsync(System.out::println)
            .thenApply(res -> state.data());   // 子图结果 → 父图状态
    })
    .addEdge(START, "subgraph")
    .addEdge("subgraph", END)
    .compile();

核心:节点函数负责双向转换 —— 父→子(喂 input) + 子→父(拿 output)。

⚠️ 中断支持由你决定:作为节点操作的子图,中断逻辑由节点函数自己处理(不是自动),适合"完全掌控子图调用方式"的场景。

5. 方式 ③ 作为状态子图(深度合并)

最紧密集成 —— 子图合并到父图,成为不可分割的一部分。父图 / 子图共享所有内容(如单一图)。

// 子图(未编译)
var childGraph = new StateGraph(ChildState.SCHEMA, ChildState::new)
    .addNode("validate", node_async(state -> ...))
    .addNode("transform", node_async(state -> ...))
    .addEdge(START, "validate")
    .addEdge("validate", "transform")
    .addEdge("transform", END);

// 父图直接 addNode(子图未编译版本) → 合并
var parentGraph = new StateGraph(ParentState.SCHEMA, ParentState::new)
    .addNode("subgraph", childGraph)            // ← 未编译
    .addEdge(START, "subgraph")
    .addEdge("subgraph", END)
    .compile();

3 个重要细节:

  1. 合并在 .compile() 时发生 —— 编译完成后子图"消失",变父图的一部分
  2. 子图节点 ID 被重命名(避免冲突)—— 父图调 getGraph() 看到的是合并后的
  3. 要拿合并后的真实 ID:用 SubGraphNode.formatId(subgraphId, subgraphNodeId)
// 中断传递 — 用重命名后的 ID
var realNodeId = SubGraphNode.formatId("subgraph", "validate");
var compileConfig = CompileConfig.builder()
    .checkpointSaver(saver)
    .interruptBefore(realNodeId)                // ← 中断合并后的子图节点
    .build();

7. 中断 + 子图

方式 ① 和 ③:子图节点自身的断点配置在子图的 CompileConfig 里,父图会继承。

方式 ③ 特殊点:合并后子图节点 ID 被重命名,父图配置中断时要用新 ID:

// 子图内部用了 "validate" 节点,带 interruptBefore
var childCompileConfig = CompileConfig.builder()
    .checkpointSaver(saver)
    .interruptBefore("validate")
    .build();

// 父图合并子图后,真实 ID = "subgraph:validate"(重命名)
var parentConfig = CompileConfig.builder()
    .checkpointSaver(saver)
    .interruptBefore("subgraph:validate")   // ← 用合并后 ID
    .build();

拿真实 ID 的标准 API:

String realId = SubGraphNode.formatId("subgraph", "validate");
compileConfig.interruptBefore(realId);

8. 可视化 + 子图

方式 ① / ②:子图是父图视图里的1 个节点(只看到入口,看不到内部)。

方式 ③:合并 —— StateGraph.getGraph() 看的是合并前(子图是 1 节点),CompiledGraph.getGraph() 看的是合并后(子图展开成内部节点)。

// 方式 ① / ②:子图作黑盒
GraphRepresentation before = parentStateGraph.getGraph(GraphRepresentation.Type.MERMAID);
System.out.println(before.getContent());   // 父图里"subgraph"是 1 个节点

// 方式 ③:合并后展开
CompiledGraph compiledParent = parentStateGraph.compile();
GraphRepresentation after = compiledParent.getGraph(GraphRepresentation.Type.MERMAID);
System.out.println(after.getContent());    // 父图里能看到子图全部节点

何时用哪种:

  • 父图视角("子图是 1 个步骤"):用 StateGraph.getGraph()
  • 子图细节(调试、Code Review):用 CompiledGraph.getGraph()

9. 流式传输 + 子图

方式流式行为
① 已编译子图✅ 自动启用(子图的 stream 自动接父图)
② 节点操作⚠️ 节点函数自己决定(stream(...).forEachAsync(...))
③ 状态子图✅ 自动启用(合并后天然支持)

10. 实战:订单处理子图

用方式 ①(已编译子图,最常用)搭一个"订单处理"子图,被"AI 客服"主图复用:

// === 子图: order_subgraph ===
public class OrderSubgraph {
    static Map<String, Channel<?>> SCHEMA = Map.of(
        "orderId",   Channel.of((o, n) -> n),                 // 覆盖
        "orderData", Channels.appender(ArrayList::new),       // 累加
        "isValid",   Channel.of((o, n) -> n),
        "paid",      Channel.of((o, n) -> n)
    );

    public static CompiledGraph build() {
        return new StateGraph<>(SCHEMA, OrderState::new)
            .addNode("validate", node_async(state -> {
                String id = (String) state.value("orderId").orElse("");
                return Map.of("isValid", !id.isBlank());
            }))
            .addNode("chargePayment", node_async(state -> {
                String id = (String) state.value("orderId").orElse("");
                // 实际业务:调支付网关
                return Map.of("paid", true, "orderData", "支付成功:" + id);
            }))
            .addConditionalEdges("validate",
                edge_async(state ->
                    (Boolean) state.value("isValid").orElse(false) ? "ok" : "bad"),
                Map.of("ok", "chargePayment", "bad", END))
            .addEdge("chargePayment", END)
            .compile();
    }
}

// === 父图: AI 客服主图 ===
public class CustomerServiceGraph {
    static Map<String, Channel<?>> SCHEMA = Map.of(
        "userMessage",  Channel.of((o, n) -> n),
        "orderId",      Channel.of((o, n) -> n),                 // 共享 key
        "orderData",    Channels.appender(ArrayList::new),       // 共享 key
        "isValid",      Channel.of((o, n) -> n),                 // 共享 key
        "finalReply",   Channel.of((o, n) -> n)
    );

    public static CompiledGraph build() {
        return new StateGraph<>(SCHEMA, MainState::new)
            .addNode("parseUserInput", node_async(state -> {
                // 解析用户消息,提取 orderId(简化)
                return Map.of("orderId", "ORD-20260622-001");
            }))
            .addNode("order_subgraph", OrderSubgraph.build())   // ← 嵌入子图(已编译)
            .addNode("formatReply", node_async(state -> {
                String data = ((List<?>) state.value("orderData").orElse(List.of()))
                    .stream().map(Object::toString).collect(Collectors.joining(";"));
                return Map.of("finalReply", "订单处理完成:" + data);
            }))
            .addEdge(START, "parseUserInput")
            .addEdge("parseUserInput", "order_subgraph")
            .addEdge("order_subgraph", "formatReply")
            .addEdge("formatReply", END)
            .compile();
    }
}

// 跑
var graph = CustomerServiceGraph.build();
var config = RunnableConfig.builder().threadId("user-001").build();
var result = graph.execute(Map.of("userMessage", "我要查订单 ORD-20260622-001"), config);
System.out.println(result);
// 输出:{userMessage=..., orderId=ORD-..., orderData=[支付成功:ORD-...], isValid=true, finalReply=订单处理完成:支付成功:ORD-...}

亮点:

  • order_subgraph 是 1 个节点(父图看),但内部 2 节点 + 1 条件边
  • 父图 / 子图共享 orderId / orderData / isValid 3 个 key
  • 子图独立编译 / 独立测试,父图只管流程编排
  • 新加"支付"子图,父图只加 1 个节点 + 1 条边

11. 实战:多智能体协调(子图作 Agent)

父图协调 3 个 Agent 子图:

// === 3 个 Agent 子图(都是已编译) ===
CompiledGraph orderAgent    = OrderAgent.build();    // 处理订单
CompiledGraph paymentAgent  = PaymentAgent.build();  // 处理支付
CompiledGraph logisticsAgent = LogisticsAgent.build(); // 处理物流

// === 主图:多 Agent 协调 ===
var mainGraph = new StateGraph(MainState.SCHEMA, MainState::new)
    .addNode("router", node_async(state -> {
        // 路由到对应 Agent(实际用 LLM 分类)
        String userMsg = (String) state.value("userMessage").orElse("");
        return Map.of("nextAgent", classify(userMsg));
    }))
    .addNode("order_agent",    orderAgent)
    .addNode("payment_agent",  paymentAgent)
    .addNode("logistics_agent", logisticsAgent)
    .addNode("respond",        node_async(state ->
        Map.of("reply", "已处理:" + state.value("agentResult").orElse(""))))

    .addEdge(START, "router")
    .addConditionalEdges("router",
        edge_async(state -> (String) state.value("nextAgent").orElse("")),
        Map.of(
            "order",     "order_agent",
            "payment",   "payment_agent",
            "logistics", "logistics_agent"
        ))
    .addEdge("order_agent",    "respond")
    .addEdge("payment_agent",  "respond")
    .addEdge("logistics_agent", "respond")
    .addEdge("respond", END)
    .compile();

多智能体价值:

  • 每个 Agent 子图独立开发 / 测试 / 部署
  • 新增 Agent(比如"投诉 Agent")= 加 1 子图 + 1 父图节点 + 1 条件边
  • 不同 Agent 可用不同 LLM(GPT-4 / Claude / 本地小模型)
  • 监控粒度:每个 Agent 独立埋点、独立超时、独立告警

12. 决策树(选哪种方式?)

13. 5 个避坑

⚠️ 坑 1:方式 ① 父图 / 子图无共享 key,通信失败
症状:addNode("sub", child.compile()) 后,子图收不到父图的 input,父图也收不到子图的 output。
根因:方式 ① 要求至少共享一个 key才能通信,完全无共享 → 通信断开。
修法:要么在父图 / 子图加共享 key;要么用方式 ②(节点操作 + 手动转换)。
⚠️ 坑 2:方式 ③ 中断配置用错 ID(子图原始名)
症状:子图里有 interruptBefore("validate"),父图继承后不生效。
根因:方式 ③ 编译时子图节点 ID 被重命名(避免冲突),父图中断要用合并后的 ID。
修法:用 SubGraphNode.formatId("subgraph", "validate") 拿真实 ID,父图 interruptBefore(realId)。
⚠️ 坑 3:方式 ② 节点操作忘了消费 stream
症状:addNode("sub", state -> compiledChild.stream(input).thenApply(...)),子图根本没跑,只跑了个空 generator。
根因:stream() 返回 lazy 的 AsyncGenerator,没消费就不会触发执行。
修法:用 .forEachAsync(...).thenApply(...) 同步消费完再返回,或者 .collectList().await()。
⚠️ 坑 4:子图返回额外 key 期望父图能拿到
症状:子图定义 schema 里有 internalDebug,子图 node 返回 Map.of("internalDebug", "..."),期望父图能 debug。
根因:子图返回的额外 key 父图会忽略(父图 schema 没定义就丢),子图收的额外 key 也忽略。
修法:要么把 key 加到父图 schema;要么在父图节点里手动 state.update("internalDebug", ...)。
⚠️ 坑 5:子图嵌套太深,debug 难
症状:"订单子图" → "支付子图" → "支付宝子图" → "签名子图",4 层嵌套,出问题不知在哪层。
根因:子图嵌套深度无限制(只看 recursionLimit),过深后 getGraph() 难读。
修法:
  • 嵌套 不超过 3 层(子图 → 父图 → 祖父图)
  • 每层加 graphId(config.graphId() 看当前在哪层)
  • 用 graph.getState(config) 看完整嵌套 state
  • 关键节点配断点(interruptBefore)逐层 review

15. 本章小结

  • 子图 = 节点的图,本质是封装 + 组合
  • 3 种添加方式:① 已编译(默认 80%)/ ② 节点操作(状态差异 15%)/ ③ 状态子图合并(深度集成 5%)
  • 方式 ① 关键:父 / 子图至少共享一个 key;额外 key 互相忽略
  • 方式 ③ 关键:编译时合并,节点 ID 重命名(用 SubGraphNode.formatId 拿真实 ID)
  • 3 大场景:大图拆小 / 多智能体协调 / 跨图复用 + 团队独立开发
  • 中断 + 流式:方式 ①/③ 自动,方式 ② 自己实现
  • 可视化:StateGraph.getGraph() 看父图视角(子图 1 节点),CompiledGraph.getGraph() 看合并后细节
一句话总结:LangGraph4j 子图 = "大图拆小 + 多智能体 + 跨图复用"。80% 用方式 ①(已编译子图),15% 用方式 ②(节点操作 + 转换),5% 用方式 ③(深度合并)。下一章(lg03 并行分支)让多个节点同时跑。
