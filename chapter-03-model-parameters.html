03Model Parameters(模型参数)

同样的 prompt,temperature=0.3 和 1.5 输出天差地别。本章讲 LangChain4j 的2 种调参方式(Builder / 配置文件)+ 6 个最常用参数。

一句话定性:模型参数 = 调创造力 / 长度 / 速度 / 成本的旋钮。LangChain4j 统一 Builder 模式,各厂商参数名略有差异,但 OpenAI 那套 6 个是行业标准。

1. 业务场景

老板:"为什么这个 AI 客服每次回答都不同?有时给长答案,有时一句话?"

根因:temperature(温度)参数没设。默认 1.0 = 模型"自由发挥"。调到 0.3 = 答案稳定 + 偏短。

调参不是开发,是产品设计。要回答"客服要稳要准"、"写作助手要发散要长"这种产品决策。

3 个真实场景的参数选择

  • AI 客服 / 代码补全 — temperature=0.0~0.3(要稳定,要准)
  • AI 写作 / 营销文案 — temperature=0.7~1.2(要发散,要创意)
  • JSON 抽取 / 分类 — temperature=0 + responseFormat=json(要结构化,要可解析)

2. 核心概念

模型参数定义 3 件事:

  • 创造性 — temperature / topP(越高越"天马行空")
  • 长度 — maxTokens / maxCompletionTokens(回答上限)
  • 成本与速度 — timeout / logRequests(调试 / 限流)

3. 2 种调参方式

方式 ① Builder 模式(代码硬编码)

OpenAiChatModel model = OpenAiChatModel.builder()
        .apiKey(System.getenv("OPENAI_API_KEY"))
        .modelName("gpt-4o-mini")
        .temperature(0.3)        // 温度(0-2,越高越发散)
        .topP(0.9)               // 核采样(0-1,跟 temperature 二选一调)
        .maxTokens(2048)          // 回答最大 token 数
        .timeout(Duration.ofSeconds(60))
        .logRequests(true)         // 打印请求体(调试用)
        .logResponses(true)        // 打印响应体
        .build();

方式 ② 配置文件(推荐,Quarkus)

# application.properties (Quarkus)
quarkus.langchain4j.openai.api-key=${OPENAI_API_KEY}
quarkus.langchain4j.openai.chat-model.temperature=0.5
quarkus.langchain4j.openai.chat-model.max-tokens=2048
quarkus.langchain4j.openai.timeout=60s

方式 ② 配置(Spring Boot)

# application.properties (Spring Boot)
langchain4j.open-ai.chat-model.api-key=${OPENAI_API_KEY}
langchain4j.open-ai.chat-model.model-name=gpt-4-1106-preview
langchain4j.open-ai.chat-model.temperature=0.3
langchain4j.open-ai.chat-model.max-tokens=1024
langchain4j.open-ai.chat-model.timeout=60s

💡 推荐做法:开发期用 Builder 调,IDE 提示全; 生产期用配置文件,改参数不用重打包,运维直接调。

4. 6 个最常用参数(OpenAI 体系)

5. 不同厂商参数差异

LangChain4j 适配 30+ 厂商,大部分参数名相同但行为有差:

  • OpenAI / 通义千问 / 智谱 GLM — temperature 范围 0~2
  • Anthropic Claude — temperature 范围 0~1(超过 1 报错)
  • 本地 Ollama — 部分模型不支持 topP

6. 选型决策树

7. 避坑指南

坑 1 · temperature 不要超过 1.5

超过 1.5 模型开始胡言乱语(语法都不通)。如果你想要"更发散",调 topP=0.95 比调 temperature=1.8 更可控。

坑 2 · logRequests 生产打开 = 信息泄露

开启 logRequests(true) 会把完整 prompt 打到日志。如果 prompt 里有用户隐私(手机号 / 身份证),直接上 ELK / 云日志 = 灾难。生产永远 false。

坑 3 · timeout 短了 → 长答直接失败

复杂 prompt(几千字输入)模型生成要 30-60 秒。timeout 设 10 秒 = 一半请求超时。生产建议 60s,流式输出可以更低(15s,看第一个 token)。

坑 4 · temperature 和 topP 不要同时大

官方建议:两个参数二选一调。都调到 1.0 = 双重发散 = 答案混乱。经验:调 temperature,topP 保持 0.9-0.95。

坑 5 · Quarkus Dev UI 可改参数但不会写回代码

Quarkus 提供一个开发期 UI(quarkus dev 后访问 /q/dev-ui),可以调参数看效果。但改了只对运行实例生效,不会写回 application.properties。验证完别忘了手动改配置文件。
